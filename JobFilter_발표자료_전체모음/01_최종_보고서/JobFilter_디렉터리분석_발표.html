아래 표는 실제 코드에서 데이터 모델, API, 화면이 모두 연결된 기능은 운영 가능, 한쪽이라도 끊긴 기능은 보완 필요, 실제 동작이 어려운 기능은 삭제/보완으로 나눴습니다.

AI 기능 현재 미적용 및 향후 검토

AI 도입 여부는 팀 내부·지인 사용자와 이야기를 나눈 끝에 현재 단계에서는 적용하지 않기로 정리했습니다. 기술적으로는 충분히 가능하지만, 지금은 다른 우선순위가 더 명확합니다. AI 도입을 완전히 닫아둔 것은 아니며, 필요한 조건이 갖춰지면 검토할 수 있습니다.

현재 AI를 쓰지 않는다는 건 의도된 선택

코드베이스를 보면 package.json에 OpenAI, Anthropic, Gemini, LangChain 등 AI 관련 의존성이 없고, .env.example에 AI 키도 없습니다. 자소서 분석 엔진(lib/cover-letter-analysis.ts)은 키워드·룰 기반으로 동작하며, 파일 상단에 "AI 없음, 서버 비용 0원"이라고 명시되어 있습니다. 공고 매칭(lib/matching.ts)도 키워드 일치, 마감일, 경력 조건을 가중치로 계산하고, 태그 추출은 미리 정한 기술 키워드와 정규식으로 합니다. UI에도 "AI가 대신 써주지 않습니다"라는 문구가 붙어 있는 것을 보면, 이는 단순히 구현을 못한 것이 아니라 의도된 방향입니다.

현재 미적용으로 정리한 이유

운영 비용 — JobFilter는 학생 대상 무료 서비스입니다. 자소서·면접·공고 매칭에 LLM API를 붙이면 월간 토큰 비용이 발생합니다. 현재 룰 기반으로 가면 서버 비용이 거의 나가지 않아 무료 운영이 가능합니다. 비용 모델과 수익 모델이 정리되면 재검토합니다.

정확성과 오해 — AI 피드백을 받은 사용자가 이를 "합격/불합격" 예측으로 받아들일 수 있습니다. 그러나 AI는 회사 문화, 채용 담당자의 취향, 이번 채용의 특수한 조건을 알 수 없습니다. AI는 "첨삭기"가 아니라 "작성 보조 피드백"으로 정확히 위치해야 하며, 그 UX와 문구를 먼저 설계해야 합니다.

개인정보와 윤리 — 자소서, 면접 답변, 포트폴리오 설명, 경험 저장소는 모두 민감한 개인정보입니다. 외부 AI API로 전송하려면 개인정보 처리 방침, 동의 절차, 보관·삭제 정책, 감사 로그 등이 갖춰져야 합니다. 현재는 이 정책 흐름이 없으므로 먼저 마련해야 합니다.

룰 기반 피드백 효과 미검증 — 11개 항목으로 피드백을 제공하고 있지만, 어떤 항목이 실제로 사용자의 문장 개선으로 이어지는지 데이터가 충분하지 않습니다. AI를 도입하기 전에 현재 룰이 어디까지 통하고 어디서 막히는지 측정하는 것이 우선입니다.

개발 범위와 우선순위 — AI 면접, AI 자소서 생성, AI 합격 예측은 각각 별도 기능입니다. 현재는 지원 현황·자소서·면접·포트폴리오의 데이터 연결과 보안 통일이 더 급해서, AI 기능은 단기 로드맵에서 제외했습니다.

룰 기반의 한계 — 현재 방식은 문맥을 이해하지 못합니다. 예를 들어 "최선을 다하겠습니다"라는 문장은 상황에 따라 진심 어린 각오일 수도, 공허한 다짐일 수도 있는데, 룰은 후자로만 잡아냅니다. AI는 이런 문맥을 더 잘 이해할 수 있지만, 현재의 비용·개인정보·오해 위험을 감수하고 급하게 도입할 단계는 아니라고 판단했습니다.

향후 AI 검토 조건

AI는 현재 미적용입니다. 다음 조건이 갖춰지면 점진적으로 검토합니다. ① 룰 기반 피드백 데이터가 충분히 쌓여 한계가 명확해질 때, ② 개인정보 동의·데이터 보관·감사 로그 정책이 마련될 때, ③ API 비용 모델과 서비스 수익 모델이 정리될 때, ④ "AI 보조 피드백"이라는 UX/문구가 확정될 때.

애로사항 / 코멘트

데이터 연결 기준 불일치

자소서의 jobId는 지원 건(JobPosting)을 연결하지만, 히트맵은 공고 DB(JobListing)를 기준으로 비교합니다. 사용자가 공고를 직접 선택하는 UX로 우선 처리했으며, 이후 모델 기준을 통일해야 합니다.

GitHub 분석 안정성

외부 URL 파싱 후 4개 GitHub API를 동시에 호출하는데 timeout, rate limit, 캐싱 강제가 없어 운영 환경에서 막힐 가능성이 큽니다. 별도 보호 로직 추가 또는 기능 제한이 필요합니다.

리크루터 기능의 정책 공백

리크루터 회원가입·승인·공고 등록은 구현되어 있지만, 학생 프로필 탐색/관심 요청/연락처 공개 동의/감사 로그 등 프라이버시 흐름이 없습니다. 학생 개인정보 보호를 위한 정책 설계가 선행되어야 합니다.

알림 신뢰성

알림이 제목·본문 문자열로만 구성되어 있어 중복 방지가 어렵고 클릭 시 이동 경로도 없습니다. 모델에 type, referenceId, actionUrl과 unique constraint를 추가해야 합니다.

코멘트: 이번 주는 화면에 기능을 추가하는 것을 넘어, 어떤 데이터를 어떻게 연결해야 사용자에게 가치를 줄 수 있는지 구조적으로 정리하는 주였습니다.
