2. 즉시 고칠 것: P0

P0-A. 인증·인가·소유권 전수 점검

문제
- API마다 인증 방식과 권한 검사가 조금씩 다르다.
- 미들웨어가 보호하는 페이지와 API 보호는 별개다.
- 사용자가 URL의 ID를 바꿔 다른 사용자의 데이터를 조회·수정하지 못하는지 전수 테스트가 필요하다.

고칠 대상
- 모든 /api/jobs/:id
- 모든 /api/cover-letter/:id
- 모든 /api/cover-letter/:id/versions
- 모든 /api/portfolio/:id
- 모든 /api/roadmap/:id
- 모든 /api/experiences/:id
- 모든 /api/interview/answers
- 모든 /api/listings/bookmark
- recruiter listing API
- admin API

수정 기준
- 먼저 세션 존재 확인
- 리소스 조회 시 userId를 where 조건에 포함
- 수정·삭제는 조회한 리소스의 소유권을 재확인
- ADMIN은 role을 서버에서 확인
- RECRUITER는 role과 isApproved를 서버에서 확인
- 클라이언트 화면의 숨김만으로 접근을 차단하지 않음

완료 체크
[ ] 다른 사용자의 JobPosting ID 조회 차단
[ ] 다른 사용자의 CoverLetter ID 조회·수정·삭제 차단
[ ] 다른 사용자의 Portfolio ID 조회·수정·삭제 차단
[ ] 다른 사용자의 Experience ID 조회·수정·삭제 차단
[ ] 다른 사용자의 RoadmapItem ID 조회·수정·삭제 차단
[ ] 미승인 리크루터의 모든 변경 API 차단
[ ] 일반 사용자의 관리자 API 차단
[ ] 비로그인 API 요청이 401을 반환
[ ] 권한 부족 API 요청이 403을 반환

P0-B. 리크루터 공고 API 입력 검증

현재 확인 대상
- app/api/recruiter/listings/[id]/route.ts

문제
- PUT 요청 body가 별도 schema 없이 바로 DB update에 사용된다.
- 날짜·URL·태그·문자열 길이·필수값 검증이 일관되지 않다.
- 잘못된 날짜가 Invalid Date가 될 수 있다.

수정
- recruiterListingSchema를 Zod로 추가한다.
- company·position 필수값 검증
- description·salary·location 길이 제한
- URL은 허용 프로토콜만 통과
- deadline은 유효한 날짜만 저장
- tags는 문자열 배열로 정규화하고 최대 개수를 제한
- 수정 시 항상 isActive=false로 재검토 상태를 유지

P0-C. 관리자 업로드 검증 강화

현재 구현
- 파일 형식 확인
- 10MB 파일 크기 제한
- 5,000행 제한
- 파싱·필터·중복 예상·dry-run

추가 수정
- MIME type과 확장자를 함께 확인
- CSV 따옴표·줄바꿈·인코딩 오류를 행 단위로 보고
- 실패 행 다운로드 기능 추가
- 날짜 파싱 실패 행 표시
- 회사+직무 중복 비교를 대소문자·공백 정규화 후 수행
- 등록 시 preview 결과와 실제 등록 결과의 차이를 보고
- createMany 실패 시 전체 실패와 부분 실패를 구분
- 업로드한 원본 파일을 DB나 공개 경로에 저장하지 않음

P0-D. 알림 중복·데이터 부작용

현재 방향
- GET /api/jobs에서 알림 생성 로직을 제거했다.
- POST /api/notifications/sync로 알림 동기화를 분리했다.

추가 수정
- body 문자열 검색에 의존하는 중복 키를 장기적으로 구조화한다.
- UserNotification에 type, referenceId, actionUrl을 추가하는 migration 검토
- type+referenceId+userId unique 기준 검토
- 알림 클릭 시 관련 지원 건으로 이동
- 동기화 실패 시 기존 알림 목록은 표시
- 오늘의 할 일과 알림이 동일 작업을 중복 표시하지 않도록 식별자 통합

P0-E. DB migration과 generated Prisma 정합성

현재 문제
- prisma/schema.prisma와 generated Prisma가 작업 과정에서 자주 변경된다.
- Experience 모델 migration이 추가되었으므로 배포 DB에 migration 적용이 필요하다.
- generated 파일을 수동 편집하면 다음 generate에서 사라진다.

수정
- schema.prisma를 유일한 모델 정의 원본으로 유지
- migration은 prisma migrate deploy로 적용
- generated Prisma 파일 직접 편집 금지
- prisma generate를 postinstall 또는 명시 명령으로 관리
- migration 적용 전 DATABASE_URL/DIRECT_URL 대상 확인
- 운영 DB backup과 migration rollback 방법을 문서화

6. 반드시 고칠 가능성이 높은 코드 문제
================================================================================

R-1. 공개 리크루터 등록 API

대상
- app/api/recruit/route.ts

확인 사항
- 공개 endpoint가 의도된 것인지 결정
- abuse 방지를 위한 rate limit
- 파일 크기·행 수 제한
- 입력 schema 검증
- 이메일 등 연락처 저장 정책
- 동일 회사·직무 중복 처리
- 관리자 검토 전 isActive=false 유지

수정 우선순위: P0

R-2. API 응답의 과다 데이터

전수 확인
- User 객체 전체 반환 여부
- password, companyDesc, email 등 불필요한 개인정보 포함 여부
- 관리자가 아닌 사용자에게 recruiter 데이터 노출 여부

수정
- 모든 API select 명시
- DTO 변환 함수 사용
- 내부 DB 모델을 그대로 JSON 반환하지 않음

R-3. 포트폴리오·GitHub 외부 URL

전수 확인
- URL protocol 제한
- github.com 도메인 제한
- timeout
- response size limit
- private repository 접근 차단
- URL redirect 검증
- 외부 응답을 HTML로 직접 렌더링하지 않음

R-4. 상태값·JSON 문자열

현재 구조
- checklist, contacts, items, skills, tags, technologies 등이 JSON 문자열로 저장됨.

개선
- 입력과 출력에 Zod schema 사용
- parse 실패 시 빈 배열로 조용히 숨기지 않고 운영 로그·사용자 안내 구분
- 상태값 enum 상수화
- 장기적으로 자주 조회되는 데이터는 별도 테이블 검토

R-5. 관리자 일괄 처리의 원자성

확인
- 일부 행 저장 후 오류가 나면 결과가 어떻게 되는지
- duplicateCount와 실제 count가 일치하는지
- 마감 공고 자동 비활성화가 예상치 않게 전체 데이터에 영향을 주지 않는지

개선
- dry-run 결과와 실제 등록 결과 분리
- transaction 또는 행별 결과 기록
- 실패 행 다운로드
- 작업 ID와 감사 로그 추가

R-6. migrations와 배포

확인
- Experience migration이 실제 배포 DB에 적용되었는지
- build에서 migrate deploy 실패 시 서비스가 어떻게 되는지
- migration 적용 전 backup 여부
- dev DB와 production DB URL 혼동 여부

9. 최종 삭제 승인 체크리스트

[ ] 배포 build가 통과한다.
[ ] 테스트가 통과한다.
[ ] 현재 Git 변경사항과 무관하다.
[ ] 필요한 문서·발표자료를 archive했다.
[ ] 삭제 대상과 이유를 작업 기록에 남겼다.
[ ] 사용자 확인이 필요한 파괴적 작업은 승인을 받았다.

10. 성공 지표
================================================================================

학생
- 공고 방문→지원 등록률
- 지원 등록→자소서 생성률
- 지원 건 준비율
- 자소서 분석→재수정률
- 체크리스트 완료율
- 면접 답변 작성률
- 오늘의 할 일 완료율
- 지원→서류합격·면접·최종합격 전환율

운영
- 업로드 실패 행 비율
- 중복 공고 비율
- 알림 중복 생성 수
- API 4xx·5xx 비율
- 외부 GitHub timeout 비율
- migration 실패 수

품질
- 주요 사용자 여정 E2E 성공률
- 타 사용자 데이터 접근 차단 테스트 성공률
- 모바일 핵심 행동 성공률
- 빈 상태·오류 상태 처리율

해석 원칙
- 매칭 점수는 합격 가능성이 아니다.
- 자소서 점수는 작성 보조 지표다.
- 통계는 표본 수와 기간을 함께 표시한다.
- 기능의 존재보다 실제 사용자 행동을 성공으로 본다.

11. 최종 결론
================================================================================

가장 먼저 할 일
1. API 인증·소유권·리크루터 승인 검증
2. Experience migration과 배포 DB 정합성 확인
3. 지원 준비 리포트 구현
4. 오늘의 할 일 상세 구현
5. 테스트 기반 확충

개선할 것
- 지원 건 중심 통합
- 로드맵·포트폴리오·경험·자소서 연결
- 업로드·알림·외부 URL 운영 안정성
- 개인정보 최소 응답
- 관리자 익명 통계

삭제·이동할 것
- 검증된 Prisma tmp 파일
- 루트의 오래된 분석·발표 산출물은 docs로 이동
- reports는 archive로 이동
- 사용처 없는 유틸·컴포넌트는 확인 후 제거
- 핵심 흐름과 무관한 AI·커뮤니티·무제한 크롤링은 보류

고칠 것
- API 입력 schema
- 권한·소유권
- JSON 데이터 검증
- migration 배포
- 파일 업로드 원자성
- GitHub URL 보안
- 테스트 부재

최종 방향
JobFilter는 페이지 수가 많은 서비스가 아니라,
학생이 공고를 발견한 뒤 준비 자료를 모으고,
지원하고,
면접을 준비하고,
결과를 분석할 수 있는 하나의 취업 준비 운영체제로 발전해야 한다.
