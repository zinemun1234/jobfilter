작성 목적
- 발표자료의 향후 발전 계획을 실제 개발 작업 단위로 정리한다.
- 기능을 무작정 추가하지 않고, 기존 기능을 하나의 취업 준비 흐름으로 연결한다.
- 작업을 페이지 1과 페이지 2로 구분하여 단계적으로 구현한다.

중요 원칙
- 현재 Git 변경사항을 먼저 보존하고, 기존 작업을 임의로 삭제하거나 되돌리지 않는다.
- 구현되지 않은 기능은 현재 기능과 구분하여 향후 기능으로 표시한다.
- 개인정보, 인증·인가, 사용자 소유권 검증을 기능 구현과 함께 확인한다.
- AI API 없이 룰 기반 분석과 기존 데이터를 우선 활용한다.
- 각 단계마다 lint, typecheck, build 및 핵심 사용자 흐름을 검증한다.

1. 전체 목표
================================================================================

최종 사용자 흐름

공고 발견
  → 맞춤 매칭 확인
  → 북마크 또는 지원 목록 추가
  → 지원 건별 준비
  → 자소서 작성·분석·수정
  → 포트폴리오·체크리스트 준비
  → 면접 연습 및 일정 관리
  → 지원 결과 기록·분석

핵심 결과
- 사용자가 한 지원 건을 준비하기 위해 여러 페이지를 반복해서 오가지 않는다.
- 매칭 점수만 보여주지 않고 점수의 근거와 부족한 준비 항목을 함께 보여준다.
- 사용자가 앱을 열었을 때 오늘 해야 할 일을 바로 확인한다.
- 기존 공고, 자소서, 면접, 포트폴리오, 로드맵 기능을 하나의 여정으로 연결한다.

페이지 1: 공고 발견과 지원 건 관리의 핵심 화면

페이지 2: 지원 준비를 완성하는 보조·확장 화면

- 페이지 2는 지원을 실제로 준비하고 완료하도록 돕는 기능을 연결하는 구간이다.
- 페이지 1의 데이터 연결이 먼저 완료되어야 페이지 2의 기능도 지원 건 중심으로 동작할 수 있다.

1-1. 페이지 1 목표

사용자가 공고를 찾고, 나에게 적합한 이유를 확인하고,
지원 목록에 추가한 뒤, 한 화면에서 준비 상태를 관리하도록 만든다.

완료 후 사용자 행동
1. 맞춤 공고 목록에서 검색·필터·정렬을 사용한다.
2. 공고 카드에서 매칭 점수와 근거를 확인한다.
3. 공고 상세에서 지원 목록에 추가한다.
4. 지원 건 상세에서 자소서·포트폴리오·체크리스트·면접 준비로 이동한다.
5. 다음 할 일을 지정하고 준비율을 확인한다.

--------------------------------------------------------------------------------
1-2. 작업 A: 매칭 계산 통합
--------------------------------------------------------------------------------

현재 문제
- 목록 화면과 대시보드의 매칭 계산 기준이 다를 가능성이 있다.
- “매칭 72%”만 표시되어 점수 산정 이유를 알기 어렵다.
- 기술 태그와 직무명 중심 계산만으로는 부족한 기술을 설명하기 어렵다.

개발 내용
- 공통 매칭 모듈을 lib/matching.ts로 통합한다.
- 기술 일치 점수와 직무 일치 점수를 분리한다.
- 경력 조건 적합 여부를 계산한다.
- 마감 임박 여부를 참고 정보로 계산한다.
- 일치 기술, 부족 기술, 적합 근거를 API 응답에 포함한다.
- 목록, 공고 상세, 대시보드 priority 공고가 같은 모듈을 사용하게 한다.

표시 예시
- 매칭 72%
- 일치 기술: React, TypeScript, Git
- 부족 기술: Docker, AWS
- 적합 근거: 신입 가능, 백엔드 직무, 마감 7일 이내

완료 기준
- 동일한 사용자와 공고에 대해 모든 화면에서 같은 점수가 표시된다.
- 점수뿐 아니라 계산 근거가 화면에 표시된다.
- 기술이 없는 사용자나 태그가 없는 공고도 오류 없이 처리된다.
- 매칭 점수가 합격 가능성 예측값이 아니라 참고 지표임을 안내한다.

1-3. 작업 B: 맞춤 공고 목록 개선
--------------------------------------------------------------------------------

현재 제공 기능
- 회사명·직무·지역 검색
- 마감 임박 및 7일 이내 마감 필터
- 신입·경력 필터
- 기술 스택 매칭 점수
- 매칭순 정렬
- 북마크
- 지원 목록 추가

개발 내용
- 검색·필터 상태를 URL query string과 연결한다.
- 공고가 많아질 경우를 대비해 서버 필터·정렬·페이지네이션을 적용한다.
- 공고 카드에 최신성, 마감일, 매칭 근거를 표시한다.
- 공고가 오래되었거나 원문 확인이 필요한 경우 안내 라벨을 표시한다.
- 북마크와 지원 목록 추가 후 성공·실패 상태를 명확히 표시한다.

완료 기준
- 새로고침 후에도 검색 조건과 필터가 유지된다.
- 공고 목록이 많아져도 전체 데이터를 한 번에 내려받지 않는다.
- 사용자는 공고 카드만 보고도 지원 여부와 적합 근거를 판단할 수 있다.

1-4. 작업 C: 지원 건 Command Center 1차
--------------------------------------------------------------------------------

목표
- 회사·직무 하나를 중심으로 지원 준비 자료를 모은다.
- 지원 공고, 자소서, 체크리스트, 면접, 포트폴리오를 하나의 흐름으로 연결한다.

화면 구성

상단 영역
- 회사명
- 직무명
- D-Day
- 현재 지원 상태
- 마감일
- 다음 할 일
- 준비율

주요 탭 또는 섹션
- 지원 정보
- 자소서
- 포트폴리오
- 체크리스트
- 면접 준비
- 일정
- 담당자
- 상태 이력
- 메모

1차 구현 범위
- 기존 JobPosting 상세 페이지를 기반으로 Command Center 진입점을 추가한다.
- 기존 자소서와 지원 건 연결 버튼을 제공한다.
- 기존 체크리스트를 지원 건 화면에서 바로 확인한다.
- 면접 질문과 답변 화면으로 이동하는 연결 버튼을 제공한다.
- 등록되지 않은 자료는 “아직 준비되지 않음” 상태로 표시한다.
- 상태 변경 시 이유·메모를 입력할 수 있도록 한다.
- 사용자가 지정한 다음 행동을 한 개 표시한다.

완료 기준
- 지원 건 상세에서 준비 관련 핵심 화면으로 한 번에 이동할 수 있다.
- 자소서, 체크리스트, 포트폴리오의 연결 상태가 보인다.
- 미완료 준비 항목과 다음 행동이 명확히 보인다.
- 기존 지원 현황 테이블·칸반 기능이 깨지지 않는다.

1-5. 작업 D: 준비율과 다음 할 일
--------------------------------------------------------------------------------

개발 내용
- 체크리스트 완료 항목 수와 전체 항목 수를 계산한다.
- 자소서 작성 여부, 포트폴리오 연결 여부, 면접 준비 여부를 준비 상태에 반영한다.
- 지원 목록 카드와 대시보드에 준비율을 표시한다.
- 마감일·면접일·팔로업일을 기준으로 다음 할 일을 정한다.
- 완료된 일정은 다시 할 일로 생성하지 않는다.

완료 기준
- 준비율 계산 기준이 문서화되어 있다.
- 목록·상세·대시보드에서 같은 준비 상태가 표시된다.
- 오늘 해야 할 일이 없을 때도 빈 상태 안내가 표시된다.

2-2. 작업 E: 자소서 코칭 연결 강화
--------------------------------------------------------------------------------

현재 제공 기능
- 분량 분석
- 공허한 표현 검사
- 수치 포함 여부
- STAR 구조 확인
- 직군 키워드 검사
- 긴 문장·반복 표현 검사
- 버전 히스토리
- JD 키워드 히트맵
- 자소서 중복 검사

개발 내용
- 분석 결과를 클릭하면 해당 문항으로 이동한다.
- 문제 문장을 하이라이트한다.
- 수정 후 선택한 항목만 재분석한다.
- 지원 건의 공고 기술 키워드와 자소서 답변을 연결한다.
- 버전 간 diff 비교와 점수 변화 그래프를 제공한다.
- 경험 저장소를 추가해 상황·행동·결과·기술·수치를 저장한다.
- 경험을 여러 자소서 문항에서 재사용할 수 있게 한다.

주의 사항
- 룰 기반 결과를 합격 판정이나 절대 평가로 표현하지 않는다.
- 문맥 이해의 한계를 안내하고 작성 보조 피드백으로 제공한다.
- 자소서 원문과 분석 결과의 공개 범위를 분리한다.

완료 기준
- 피드백에서 실제 수정 위치까지 이동할 수 있다.
- JD 요구 키워드가 어느 문항에 반영되었는지 확인할 수 있다.
- 버전별 변경 내용과 점수 변화를 확인할 수 있다.

2-3. 작업 F: 면접·포트폴리오 지원 건 연결
--------------------------------------------------------------------------------

면접 개발 내용
- 기술·인성·상황 질문 필터를 제공한다.
- 프론트엔드·백엔드·공통 직무 필터를 제공한다.
- 지원 건별 추천 질문 목록을 표시한다.
- 답변 저장과 커스텀 질문을 지원한다.
- 모의 면접 결과를 지원 건 이력에 기록한다.

포트폴리오 개발 내용
- 프로젝트를 지원 건에 연결한다.
- 대표 프로젝트를 지정한다.
- 기술 스택, GitHub URL, 배포 URL을 표시한다.
- GitHub 공개 저장소 분석 결과를 연결한다.
- README, 사용 언어, 커밋, 최근 활동 정보를 보여준다.
- 지원 건별 포트폴리오 export를 제공한다.

완료 기준
- 특정 지원 건에서 관련 면접 질문과 대표 포트폴리오를 바로 확인한다.
- GitHub URL 오류, 비공개 저장소, timeout을 안전하게 처리한다.
- 외부 URL 요청에 허용 도메인과 timeout 제한을 적용한다.

2-4. 작업 G: 오늘의 할 일과 통합 알림
--------------------------------------------------------------------------------

현재 문제
- 마감·면접·팔로업 알림이 화면 조회와 함께 생성될 수 있다.
- GET 요청에 데이터 생성 부작용이 있으면 중복과 운영 비용이 증가한다.
- 알림 내용을 문자열 비교로 중복 판단하는 방식은 취약하다.

개발 내용
- 알림에 type, referenceId, actionUrl을 구조화해 저장한다.
- GET 요청에서 알림을 생성하지 않도록 분리한다.
- 알림 생성은 일정 동기화 또는 명시적인 작업에서 수행한다.
- type과 referenceId 조합으로 중복을 방지한다.
- 오늘의 할 일에 마감·면접·팔로업·체크리스트를 통합한다.
- 알림 클릭 시 해당 지원 건 또는 준비 화면으로 이동한다.

완료 기준
- 목록 페이지를 여러 번 열어도 동일 알림이 중복 생성되지 않는다.
- 알림을 클릭하면 관련 지원 건의 정확한 화면으로 이동한다.
- 사용자가 알림을 확인한 뒤 상태 변경·체크리스트 완료를 수행할 수 있다.

--------------------------------------------------------------------------------
2-5. 작업 H: 로드맵·대시보드 연결
--------------------------------------------------------------------------------

개발 내용
- 목표 직무별 기술 로드맵 진행률을 표시한다.
- 최근 공고에서 자주 요구되는 기술과 사용자의 기술 차이를 비교한다.
- 부족한 기술을 학습 항목으로 제안한다.
- 학습 완료를 GitHub 프로젝트나 포트폴리오 증거와 연결한다.
- 대시보드에 지원 현황, 긴급 마감, 우선순위 공고, 오늘의 할 일을 배치한다.

완료 기준
- 로드맵이 독립적인 체크리스트가 아니라 지원 공고와 연결된다.
- 대시보드에서 지금 처리해야 할 지원 건을 우선 확인할 수 있다.
- 우선순위 산정 기준이 사용자에게 설명된다.

--------------------------------------------------------------------------------
2-6. 작업 I: 관리자 업로드 품질 개선
--------------------------------------------------------------------------------

개발 내용
- Excel/CSV 업로드 전 미리보기를 제공한다.
- 컬럼 자동 매핑 결과를 관리자가 확인한다.
- 포함·제외·중복·파싱 실패 행을 구분한다.
- 실패 행을 다운로드할 수 있게 한다.
- 날짜 형식, 인코딩, 필수 필드 오류를 표시한다.
- 실제 등록 전 dry-run 결과를 제공한다.
- IT·개발 관련 포함·제외 키워드 규칙을 관리자 화면에서 관리한다.

완료 기준
- 잘못된 파일을 업로드해도 기존 공고 데이터가 손상되지 않는다.
- 관리자가 등록 전 성공·실패 행을 확인할 수 있다.
- 중복 공고 처리 기준이 명확하다.

--------------------------------------------------------------------------------
2-7. 작업 J: 리크루터와 개인정보 보호
--------------------------------------------------------------------------------

개발 내용
- 리크루터 가입·관리자 승인 상태를 서버에서 강제한다.
- 승인된 리크루터만 공고를 등록·수정·삭제할 수 있게 한다.
- 학생별 공개 동의 필드를 세분화한다.
- 이메일 등 민감정보를 기본 비공개로 유지한다.
- 공개 동의 학생의 마스킹 프로필 검색 화면을 만든다.
- 리크루터의 관심 요청과 학생 수락 흐름을 만든다.
- 모든 검색·조회·요청 API에서 role, isApproved, 소유권을 검사한다.

완료 기준
- 미승인 리크루터가 API를 직접 호출해도 변경할 수 없다.
- 학생은 공개 범위를 직접 관리할 수 있다.
- 기업은 학생의 명시적 동의 없이 민감정보를 확인할 수 없다.
- 관심 요청과 수락 이력이 남는다.

4. 공통 기술·품질 기준
================================================================================

인증·인가
- 모든 API에서 로그인 여부를 확인한다.
- 리소스 소유권을 서버에서 확인한다.
- ADMIN, USER, RECRUITER 역할을 분리한다.
- 리크루터 isApproved 상태를 서버에서 강제한다.

데이터 검증
- JSON 문자열 입력·출력 schema를 공통화한다.
- 날짜·URL·배열·상태값을 API 경계에서 검증한다.
- 사용자가 보낸 ID만 믿지 않고 DB에서 접근 권한을 재검증한다.

외부 요청
- GitHub 및 원문 URL 요청에 timeout을 둔다.
- 허용 도메인 외 요청을 차단한다.
- 실패 시 사용자에게 재시도 가능한 메시지를 제공한다.
- 비밀키와 개인정보를 로그에 기록하지 않는다.

성능·운영
- 공고 목록에 페이지네이션을 적용한다.
- GET 요청에 쓰기 부작용을 두지 않는다.
- 알림 중복 방지 기준을 구조화한다.
- 파일 업로드 크기와 행 수를 제한한다.
- 오류 모니터링과 핵심 이벤트 측정을 추가한다.

테스트 대상
- 매칭 점수 계산
- 준비율 계산
- 자소서 분석 규칙
- 자소서 중복 검사
- 체크리스트 상태 변경
- API 소유권 검사
- 관리자·리크루터 권한 검사
- 알림 중복 방지
