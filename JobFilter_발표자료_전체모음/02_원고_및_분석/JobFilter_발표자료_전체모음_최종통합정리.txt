1. 문서 목적과 발표 기준
================================================================================

이 문서는 JobFilter 발표자료 전체모음 폴더 안의 모든 분석서·계획서·작업 보고서·reports를 하나의 발표 기준으로 통합한 것이다. 발표할 때는 이 TXT 본문을 원고처럼 읽고, PDF와 이미지는 보조 시각 자료로 쓰면 된다.

가장 중요한 것은 “기능 목록을 읽는 발표”가 되지 않도록 하는 것이다. 각 기능을 왜 만들었고, 어떻게 동작하고, 무엇이 아직 부족한지, 다음에 무엇을 해야 하는지를 하나의 취업 준비 흐름으로 설명해야 한다.

기능 분류 기준은 다음과 같이 적용했다.

[분류: 현재 구현] — 실제 소스와 API에서 동작을 확인한 기능
[분류: 1차 구현] — 핵심 흐름은 연결됐지만 데이터 직접 연결이나 운영 검증이 남은 기능
[분류: 개선 완료] — 이번 작업에서 구조적으로 개선하고 검증한 기능
[분류: 삭제 완료] — 잘못 추가되거나 핵심 흐름과 무관해 제거한 기능
[분류: 보완 필요] — 기능은 있으나 보안·성능·정합성·운영 적용 등 추가 보강이 필요한 기능
[분류: 향후 계획] — 기획·화면 이동·부분 기반만 있고 아직 완성하지 않은 기능

이 기준은 발표뿐 아니라 앞으로 개발할 때도 동일하게 적용해야 한다. “버튼이 있다”고 “구현됐다”고 말하지 않고, “사용자가 끝까지 쓸 수 있는가”를 기준으로 판단해야 한다.

2. JobFilter를 만들게 된 배경과 해결하는 문제
================================================================================

JobFilter는 처음에는 “학교에서 주는 공고 중 컴퓨터·IT·개발 직무를 찾아주는 필터”로 시작했다. 그런데 개발을 진행하면서 점점 더 중요한 문제가 보였다. 공고를 찾는 것보다 공고를 찾은 뒤의 준비 과정이 훨씬 복잡하고, 그 과정이 여러 화면과 메모로 흩어져 있다는 것이다.

학생 입장에서 취업 준비를 시작하면 먼저 공고를 찾아야 한다. 학교에서 받는 공고 파일에는 개발직과 사무직, 영업·서비스 직무가 섞여 있다. 회사명이나 직무명 표기도 일정하지 않아서 학생이 직접 한 줄씩 걸러봐야 한다.

공고를 하나 찾았다고 해서 끝이 아니다. 자소서를 써야 하고, 포트폴리오를 정리해야 하고, 면접 질문을 준비하고, 마감일과 면접일과 팔로업 일정도 기억해야 한다. 이 자료들이 각각 다른 화면이나 문서·메모에 흩어져 있으면 학생은 같은 정보를 반복해서 입력하게 된다. 지원한 회사가 어디인지, 자소서를 만들었는지, 체크리스트를 끝냈는지, 면접 준비를 했는지 한 번에 보기 어렵다.

JobFilter가 해결하려는 문제를 여섯 가지로 정리하면 다음과 같다.

1. 학교 Excel 공고가 복잡하다. 직무가 섞여 있고, 날짜·컬럼·중복 형식이 일정하지 않다.
2. 나에게 맞는 공고인지 판단하기 어렵다. 공고가 많은데 점수 계산 근거가 보이지 않는다.
3. 지원 준비 자료가 분산된다. 자소서·면접·포트폴리오·일정이 별도 페이지다.
4. 자소서 피드백이 편집으로 연결되지 않는다. 문제 문장을 다시 찾아야 한다.
5. 경험을 반복 입력한다. 한 번 쓴 프로젝트 경험을 다른 자소서에서 쉽게 재사용할 수 없다.
6. 마감일·면접일·팔로업을 놓치기 쉽다. 알림과 할 일 관리가 끊긴다.

이 문제들을 해결하려면 공고 탐색만 잘 되는 것이 아니라, 공고 발견부터 지원 준비·지원·후속 관리·결과 분석까지 하나의 지원 건 중심 흐름으로 연결해야 한다. JobFilter의 현재 목표도 바로 그것이다.

3. 기술 스택과 아키텍처 개요
================================================================================

JobFilter는 Next.js 14 App Router, React, TypeScript, Tailwind CSS, shadcn/ui, Prisma, PostgreSQL, NextAuth.js, Vercel을 기반으로 한다. 이 조합을 선택한 이유는 학교 팀이나 소규모 운영에서 하나의 코드베이스로 SSR·CSR·API Routes를 모두 처리할 수 있어서 운영 부담이 적기 때문이다.

아키텍처는 크게 세 계층으로 볼 수 있다.

- 프레젠테이션 계층: app/(dashboard), app/(admin), app/(recruiter), app/(auth) 등의 페이지. shadcn/ui와 Tailwind CSS로 일관된 카드·폼·테이블 UI를 구성한다.
- API/비즈니스 계층: app/api/* 경로의 Next.js API Route. 인증·공고·지원·자소서·면접·포트폴리오·로드맵·알림·관리자·리크루터 API가 존재한다.
- 데이터 계층: Prisma ORM + PostgreSQL. prisma/schema.prisma에 정의된 JobPosting, CoverLetter, CoverLetterVersion, Experience, Portfolio, InterviewQuestion, InterviewAnswer, RoadmapItem, JobListing, JobBookmark, UserNotification 등의 모델이 핵심 데이터를 관리한다.

인증은 NextAuth.js Credentials Provider로 이메일+비밀번호를 처리하고, bcryptjs로 비밀번호를 해싱한다. JWT 세션에 user.id와 user.role을 포함하고, middleware.ts에서 /admin, /dashboard 등의 접근을 제한한다. 보안은 “클라이언트에서 버튼을 숨기는 것”이 아니라 각 API Route에서 세션·role·userId 소유권을 서버에서 검증하는 방식으로 구현했다.

기술 스택에서 한 가지 원칙을 강조하고 싶다. JobFilter는 AI API를 사용하지 않는다. 자소서 코칭·공고 필터링·키워드 추출·우선순위 산정·매칭 점수 등 핵심 기능은 모두 키워드 매칭·정규표현식·룰 기반으로 구현했다. 이는 학생 대상 무료 서비스에서 월간 API 비용 없이 지속 운영할 수 있도록 하기 위한 선택이다. 다만 룰 기반 분석은 문맥을 완전히 이해하지 못하므로, 발표에서는 “AI 합격 판정”이 아니라 “작성 보조 피드백”이라고 정확히 말해야 한다.

DB 구조에서는 checklist, contacts, items, skills, tags, technologies, analysisHistory 등이 JSON 문자열로 저장된다. 이 방식은 migration을 줄이고 빠르게 구현할 수 있다는 장점이 있지만, schema 검증·검색·집계가 어렵다는 단점도 있다. 따라서 입력과 출력에 Zod schema를 적용하고, 장기적으로 자주 조회되는 데이터는 별도 테이블로 분리하는 방향을 고려해야 한다.

4. 페이지별 기능 흐름
================================================================================

JobFilter는 크게 두 페이지 그룹으로 나눌 수 있다. Page 1은 공고 발견과 지원 건 관리의 핵심 화면이고, Page 2는 지원 준비를 완성하는 보조·확장 화면이다.

--------------------------------------------------------------------------------
Page 1: 공고 발견·지원 관리
--------------------------------------------------------------------------------

Page 1의 목표는 사용자가 공고를 찾고, 나에게 적합한 이유를 확인하고, 지원 목록에 추가한 뒤 한 화면에서 준비 상태를 관리하는 것이다.

- /listings: 맞춤 공고 목록. 회사명·직무·지역 검색, 마감 임박·7일 이내 필터, 신입·경력 필터, 기술 스택 기반 매칭순 정렬, 북마크, 지원 목록 추가.
- /listings/[id]: 공고 상세. 지원 목록에 추가, 자소서 작성 화면으로 연결.
- /jobs: 지원 현황 테이블·칸반. 지원 공고 등록·수정·삭제, 상태 이력, 담당자·마감·면접·팔로업, 체크리스트.
- /jobs/[id]: 지원 건 상세. Command Center, 상태·체크리스트·일정, 준비율, 자소서·면접·포트폴리오·일정 빠른 이동.

Page 1의 핵심 흐름은 다음과 같다.

공고 발견 → 맞춤 매칭 확인 → 북마크 또는 지원 목록 추가 → 지원 건별 준비 → 다음 할 일 확인

Page 1의 데이터 연결이 먼저 완료되어야 Page 2의 기능도 지원 건 중심으로 동작할 수 있다.

--------------------------------------------------------------------------------
Page 2: 지원 준비·분석·운영 확장
--------------------------------------------------------------------------------

Page 2는 공고를 선택한 뒤 실제로 준비를 완성하도록 돕는 기능을 연결하는 영역이다.

- /cover-letter: 자소서 작성, 룰 기반 분석, JD 키워드 히트맵, 중복 검사, 버전 diff, 경험 저장소 삽입, PDF export.
- /interview: 면접 질문·답변, 모의 면접, 질문 추가.
- /portfolio: 프로젝트 등록, GitHub 분석, PDF export.
- /roadmap: 직무별 기술 학습 로드맵.
- /calendar: 마감·면접·팔로업 일정.
- /notifications: 알림 목록·읽음 처리, 동기화.
- /dashboard: 지원 현황 요약, 우선순위 공고, 로드맵 진행률, 오늘의 할 일 1차.
- /admin/*: 관리자 공고 업로드·일괄 처리·사용자·공지·질문·통계·취업 기록.
- /recruiter: 승인된 리크루터의 공고 등록·수정·삭제.

Page 2의 핵심 흐름은 다음과 같다.

지원 건 선택 → 자소서 작성·분석·수정 → 경험 재사용 → 포트폴리오·체크리스트 준비 → 면접 연습 및 일정 관리 → 지원 결과 기록·분석

현재 Page 1의 핵심 연결은 구현됐지만, Page 2의 포트폴리오·면접 답변이 지원 건에 직접 연결되는 부분은 아직 1차 구현 수준이다.

5. 주요 기능 상세 분석
================================================================================

이 섹션에서는 각 기능을 [분류] 태그와 함께 “문제 → 구현 → 동작 → 사용자 가치 → 현재 한계 → 다음 단계” 순서로 설명한다.

--------------------------------------------------------------------------------
5-1. 설명 가능한 매칭 점수
[분류: 현재 구현]
--------------------------------------------------------------------------------

문제: 학생이 공고를 볼 때 “매칭 72%”라는 숫자만 보면 왜 72%인지, 무엇이 부족한지 알 수 없다. 목록 화면과 대시보드가 서로 다른 기준으로 점수를 계산할 가능성도 있었다.

구현: lib/matching.ts에 calculateMatching 순수 함수를 만들어 공통 매칭 모듈로 통합했다. 사용자 skills와 공고 tags를 문자열 정규화한 뒤 교집합으로 일치 기술을, 공고에는 있지만 사용자에게 없는 기술을 부족 기술로 계산한다. 목표 직무와 공고 직무명의 유사도, career 조건(신입·무관·인턴), 마감 긴급도를 함께 반영한다. 목록 API와 대시보드 우선순위 API가 같은 모듈을 호출하도록 바꿨다.

동작: 공고 카드에 매칭 점수, 일치 기술, 부족 기술, 적합 근거가 함께 표시된다. 예를 들어 “매칭 72%, 일치 기술: React, TypeScript, Git, 부족 기술: Docker, AWS, 적합 근거: 신입 가능, 직무 유사, 마감 임박”처럼 보인다.

사용자 가치: 학생은 “이 공고가 나에게 맞는가”뿐만 아니라 “지원하기 전에 무엇을 더 준비해야 하는가”를 동시에 알 수 있다. 점수가 화면마다 달라지는 혼란도 줄었다.

현재 한계: 기술 이름의 동의어나 의미까지 완전히 이해하지 못한다. 공고 tags가 잘못 추출되면 매칭 결과도 영향을 받는다. 대량 공고에 대한 서버 페이지네이션과 검색 최적화는 추가로 필요하다.

다음 단계: 매칭 점수의 “정보 신뢰도” 항목을 추가하고, 기술 동의어 사전을 보강하며, 대시보드 우선순위 점수와 목록 매칭 점수의 계산 기준과 가중치를 문서화한다.

발표할 때 꼭 말해야 할 것: “이 점수는 합격 가능성을 예측하는 점수가 아닙니다. 학생의 기술과 공고의 요구사항을 비교한 참고 지표입니다.”

현재 한계: 현재는 화면 이동과 자소서 연결이 중심이다. 포트폴리오와 면접 답변이 지원 건 데이터로 직접 집계되는 부분은 아직 향후 작업이다.

다음 단계: /jobs/[id]에서 지원 건별 대표 포트폴리오, 면접 답변 수, 경험 연결 수를 실제로 집계하고, 부족한 항목을 클릭하면 해당 페이지로 이동한다.

동작: 지원 건 상세와 목록·대시보드에 준비율이 표시된다. 미완료 항목과 다음 행동이 명확히 보인다.

다음 단계: 자소서 분석 점수, 포트폴리오 대표 프로젝트, 면접 답변 작성 수, 경험 연결 수를 준비율에 추가하고, 계산 규칙을 공통 함수로 관리한다.

5-4. 알림 시스템 (GET 부작용 분리, 중복 방지, Today’s Tasks)

문제: GET /api/jobs 조회 시 알림을 생성했기 때문에, 목록을 새로고침할 때마다 DB 조회·쓰기와 중복 확인이 반복될 수 있었다. 조회만 해도 쓰기가 발생하는 부작용이 있었다.

구현: GET /api/jobs에서는 조회만 수행하고, POST /api/notifications/sync에서 알림 동기화를 분리했다. 알림 페이지는 동기화 후 목록을 조회한다. 중복 방지는 body 문자열 contains 검색에서 장기적으로 type·referenceId·actionUrl 구조로 마이그레이션할 계획이다.

동작: 마감 준비, 면접 준비, 팔로업 확인, 미완료 준비물 확인 등의 알림이 생성된다. 대시보드에는 지원 건의 마감·면접·팔로업·미완료 체크리스트를 기반으로 오늘의 할 일 1차 목록이 표시된다.

사용자 가치: 새로고침해도 같은 알림이 계속 생기지 않고, 사용자가 앱을 열었을 때 오늘 해야 할 일을 바로 볼 수 있다.

현재 한계: 알림 중복 키가 아직 body 문자열 검색 기반이다. 장기적으로 UserNotification에 type, referenceId, actionUrl 컬럼과 unique 기준을 추가해야 한다. 오늘의 할 일과 알림이 동일 작업을 중복 표시하지 않도록 식별자 통합이 필요하다.

다음 단계: 알림 모델을 구조화하고, 동기화 실패 시에도 기존 알림 목록이 표시되도록 하며, 알림 클릭 시 관련 지원 건으로 이동한다.

동작: 관리자는 업로드한 파일의 첫 20행 샘플, 필수 컬럼 누락 경고, 날짜·인코딩·중복·제외 사유, 성공·실패·스킵 행 통계를 본 뒤 선택적으로 등록한다.

다음 단계: 실패 행 다운로드 기능과 행별 결과 기록, transaction 처리, dry-run 결과와 실제 등록 결과 분리를 보강한다.

5-7. 자소서 룰 기반 코칭

동작: 학생이 자소서를 작성하면 11가지 항목을 분석해 피드백을 준다. 피드백 메시지에서 따옴표 안의 표현을 추출해, 해당 문항으로 스크롤하고 문제 문장을 하이라이트한다. 수정 후 재분석하면 피드백이 갱신된다.

사용자 가치: AI API 비용 없이 1차 피드백을 받을 수 있고, 피드백과 편집 화면이 직접 연결되어 실제 수정 행동으로 이어진다.

현재 한계: 문맥을 완전히 이해하는 AI가 아니다. 점수를 억지로 높이기 위해 키워드나 숫자를 과다하게 넣을 수 있다. 룰 기반 분석의 한계를 화면에 명확히 표시해야 한다.

다음 단계: JD 기반 자소서 준비 흐름을 강화하고, 공고 상세에서 “이 공고로 자소서 시작”을 누르면 회사·직무·JD 키워드·체크리스트를 자소서에 연결한다.

5-9. 경험 저장소 (Experience Library)
[분류: 현재 구현]
--------------------------------------------------------------------------------

문제: 상황·행동·결과·사용 기술·성과를 자소서마다 반복 입력해야 했다. 경험은 한 번 쓰고 버리는 정보가 아닌데, 재사용할 공간이 없었다.

구현: Prisma Experience 모델에 id, userId, title, situation, action, result, technologies, metrics, createdAt, updatedAt 필드를 추가하고 migration을 생성했다. app/api/experiences/*에서 CRUD API를 구현하고, userId 소유권 검증과 입력 길이 검증, 응답 DTO에서 userId 제외를 적용했다. 자소서 작성 화면에서 SlideOver로 경험 목록을 보고 첫 문항에 STAR 텍스트를 삽입할 수 있다.

동작: 학생이 “팀 프로젝트 성능 개선” 같은 경험을 상황·행동·결과·기술·성과로 저장하면, 나중에 자소서 문항에서 해당 경험을 선택해 삽입한다.

사용자 가치: 프로젝트 경험을 한 번 구조화해두고 여러 자소서 문항과 면접 답변, 포트폴리오 설명에 재사용할 수 있다.

현재 한계: Experience migration 파일이 실제 운영 DB에 적용됐는지는 아직 확인하지 않았다. 자소서 삽입 외에 면접 답변·포트폴리오와의 직접 연결은 아직 미구현이다.

다음 단계: 운영 DB에 migration이 적용됐는지 확인하고, 경험을 면접 답변과 포트폴리오 설명에도 삽입할 수 있도록 연결한다.

--------------------------------------------------------------------------------
5-10. 리크루터·공개 구인 API (입력 검증, 보안, rate limit)
[분류: 현재 구현]
--------------------------------------------------------------------------------

문제: 리크루터와 공개 구인 등록 API의 입력 검증이 일관되지 않았고, URL·날짜·이메일·문자열 길이 제한이 부족했다. 공개 endpoint에 대한 abuse 방지도 필요했다.

구현: app/api/recruiter/listings/[id]/route.ts에 Zod 기반 recruiterListingSchema를 추가해 company·position 필수값, description·salary·location 길이 제한, URL 허용 프로토콜, deadline 유효 날짜, tags 문자열 배열 정규화·최대 개수 제한을 검증한다. 수정 시 항상 isActive=false로 재검토 상태를 유지한다. app/api/recruit/route.ts와 리크루터 가입 API에는 rate limit을 적용했고, 공개 구인 파일 업로드에는 크기·행 수 제한을 적용했다.

동작: 리크루터는 가입 후 관리자 승인을 받아야 공고를 등록·수정·삭제할 수 있다. 승인된 계정만 변경할 수 있고, 수정한 공고는 관리자 재검토 후 노출된다.

사용자 가치: 학생은 승인된 기업의 공고만 볼 수 있고, 잘못된 입력이나 악의적 요청으로부터 서비스를 보호할 수 있다.

현재 한계: 실제 학생 탐색 화면은 아직 없다. 학생 공개 동의가 UI 토글 중심이면 서버 정책과 불일치할 수 있어 DB 저장과 API 강제 적용이 필요하다.

다음 단계: 학생별 공개 동의 필드 세분화, 이메일·전화번호 기본 비공개, 조회·관심 요청 감사 로그, 학생 수락 전 직접 연락 차단 정책을 확정한 뒤 리크루터 학생 탐색 기능을 구현한다.

--------------------------------------------------------------------------------
5-11. API 에러·권한 표준화
[분류: 보완 필요]
--------------------------------------------------------------------------------

문제: API마다 인증 방식과 권한 검사가 조금씩 다르고, 일부 API는 Prisma 객체를 spread해서 반환해 의도하지 않은 개인정보가 포함될 수 있다. 404와 403 기준, 오류 응답 형식이 완전히 통일되지 않았다.

구현: JobPosting 상세 조회에 id와 userId 조건을 함께 사용하고, Experience 조회·수정·삭제에 userId를 사용하며, Recruiter 공고에 recruiterId 소유권을 확인하고, Admin API에 ADMIN role 확인, Recruiter API에 role과 isApproved 확인을 적용했다. lib/auth.ts, lib/api.ts, lib/errors.ts에 공통 인증·응답·오류 처리를 시작했다.

동작: 일반적으로 세션 존재 확인 → 리소스 조회 시 userId where 조건 → 수정·삭제 시 소유권 재확인 → ADMIN/RECRUITER role 서버 확인 순서로 동작해야 한다.

사용자 가치: 다른 사용자의 데이터가 노출되거나 악의적으로 수정되는 위험을 줄일 수 있다.

현재 한계: 전체 API에 대한 통합 권한 테스트는 아직 없고, DTO 전수 정리는 미완료다. 일부 API에서 User 객체 전체를 반환하거나 password·companyDesc·email 등 불필요한 개인정보를 포함할 수 있다. 메모리 기반 rate limiter는 Vercel 다중 인스턴스 환경에서 전역 제한이 아니다.

다음 단계: Vitest에서 세션과 Prisma를 mocking한 API 통합 권한 테스트를 작성한다. 401·403·404 응답 기준을 문서화하고, JobPosting·Portfolio·JobListing·User 응답 DTO를 공통화한다. 외부 URL 요청에 timeout·도메인·응답 크기 제한을 전수 점검한다.

--------------------------------------------------------------------------------
5-12. 포트폴리오·면접·일정 연결
[분류: 1차 구현]
--------------------------------------------------------------------------------

문제: 포트폴리오와 면접 답변이 지원 건에 직접 연결되지 않아, 지원 준비율이나 Command Center에서 실제 준비 상태를 완전히 보여줄 수 없었다.

구현: 현재 포트폴리오 등록·기술 스택·GitHub 공개 저장소 분석·PDF export, 면접 질문·답변·모의 면접, 캘린더 마감·면접·팔로업 일정 관리 기능은 각각 구현되어 있다. Command Center에서는 이들 화면으로 이동하는 연결 버튼을 제공한다.

동작: 학생은 /portfolio에서 프로젝트를 등록하고 GitHub 분석 카드를 볼 수 있고, /interview에서 질문에 답변하고 모의 면접을 연습하며, /calendar에서 일정을 관리할 수 있다.

사용자 가치: 포트폴리오의 GitHub 활동을 객관적 증거로 보여주고, 면접 답변을 저장·복습할 수 있다.

현재 한계: 포트폴리오와 면접 답변이 지원 건별로 직접 연결되지 않는다. JD/지원 공고 기준으로 질문 묶음을 생성하거나, JD 요구 기술과 프로젝트 기술의 일치를 보여주는 기능은 아직 향후 작업이다.

다음 단계: JobPosting과 Portfolio·InterviewAnswer를 직접 연결하거나 지원 건별 연결 테이블을 만든다. 지원 건별 면접 준비, 회사/직무/JD 기반 질문 묶음, 대표 포트폴리오 지정 기능을 구현한다.

--------------------------------------------------------------------------------
5-13. 별도 /today 페이지
[분류: 삭제 완료]
--------------------------------------------------------------------------------

별도 /today 페이지를 만들라는 요청이 아니었는데 한때 잘못 해석해 app/(dashboard)/today/page.tsx, lib/today-tasks.ts, lib/today-tasks.test.ts를 생성했다. 사용자 요청에 따라 이 파일들을 제거했고, 대시보드의 /today 링크도 제거했다. 현재 실제 구현으로 남아 있는 것은 대시보드 안의 오늘의 할 일 1차 영역뿐이다.

발표나 시연에서 별도 /today 페이지를 언급하거나 보여서는 안 된다.

6. 웹 조사에서 얻은 외부 사례와 JobFilter 적용 방향
================================================================================

JobFilter 추가 페이지를 검토할 때 참고한 외부 사례를 정리한다. 단, 외부 서비스를 그대로 복제하지 않고 컴퓨터정보과·인공지능소프트웨어과 학생이라는 대상에 맞게 축소·재해석해야 한다.

--------------------------------------------------------------------------------
6-1. 지원 추적·애플리케이션 관리
--------------------------------------------------------------------------------

참고: Apply Tracker, jobtrackit.com 등
외부 사례: Kanban 보드로 Applied, Interviewing, Offer Received 단계를 관리하고, 인터뷰 리마인더, 제안 조건 기록·비교, 응답 시간·전환율·지원 퍼널 분석, ATS 이력서 검사, 커버레터와 이력서 관리 기능을 제공한다.

JobFilter 적용 방향: 기본 상태 관리는 이미 있으므로 단순 Kanban 추가는 차별성이 낮다. 대신 지원 건별 준비율, 상태별 전환율, 제안 비교처럼 현재 데이터와 연결되는 기능이 우선이다. 지원 활동 분석 페이지는 이 맥락에서 P1으로 설정했다.

--------------------------------------------------------------------------------
6-2. 학생용 취업 준비 워크스페이스
--------------------------------------------------------------------------------

참고: Notion Students’ Job Application Tracker System
외부 사례: 지원 상태 추적, 회사 데이터베이스, 네트워킹 연락처 관리, 포트폴리오·CV·자소서 자료 관리, 개인 취업 대시보드 기능을 제공한다.

JobFilter 적용 방향: 지원 건 Command Center 방향이 타당하다. 담당자 연락처와 팔로업 날짜를 이미 보유하고 있으므로 네트워킹 관리로 확장할 기반이 있다. 다만 소셜 네트워크 기능을 새로 만들기보다 지원 건의 담당자·후속 연락 관리에 집중한다.

--------------------------------------------------------------------------------
6-3. 대학 커리어 서비스 플랫폼
--------------------------------------------------------------------------------

참고: VIAS Career Services, studentfirst.com Career Services
외부 사례: 학생 취업 진행 상황 관리, 공고 및 이력서 검토, 취업 박람회·네트워킹 이벤트, 기업 관계·연락처 관리, 취업 결과 보고서·분석 기능을 제공한다.

JobFilter 적용 방향: 관리자용 학생 취업 지원 페이지가 유용하다. 학교 운영자는 공고 수보다 학생이 어느 단계에서 막히는지 확인해야 한다. 개인정보를 최소화한 집계형 통계부터 제공해야 한다.

--------------------------------------------------------------------------------
6-4. ATS·직무 준비
--------------------------------------------------------------------------------

참고: JobScan ATS tips for students, apply-tracker ATS resume check
외부 사례: ATS 구조·헤딩·연락처·키워드·문서 형식 점검, 공고와 이력서·자소서 키워드 비교, 약한 부분과 개선 방향 제공, 직무별 이력서·면접 질문·회사 리뷰 자료 연결.

JobFilter 적용 방향: 현재 자소서 룰 기반 코칭과 JD 키워드 히트맵은 좋은 기반이다. 다음에는 자소서만 점수화하지 말고 지원 건의 “준비 증거”를 보여주는 것이 좋다. 자동 합격 예측이나 AI 대필이 아니라 체크 가능한 근거 중심으로 유지한다.

--------------------------------------------------------------------------------
6-5. 지원 퍼널·포트폴리오·기술 증거
--------------------------------------------------------------------------------

외부 사례에서 반복적으로 보이는 것은 “기술을 가졌다고 말하는 것보다 증거를 보여주는 것”이다. GitHub, 배포 URL, README, 커밋 활동, 프로젝트 결과물이 기술 증거가 된다.

JobFilter 적용 방향: 포트폴리오에 GitHub 분석 카드를 추가한 것이 시작이다. 다음에는 공고 tags와 사용자 skills 비교 후, 해당 기술을 증명할 수 있는 포트폴리오·경험·로드맵 항목을 매핑한다. “Docker가 부족합니다”에서 끝나는 것이 아니라 “Docker를 요구하는 공고가 있고, 아직 관련 포트폴리오 증거가 없습니다”까지 보여주는 것이 목표다.

--------------------------------------------------------------------------------
6-6. 면접 회고·팔로업
--------------------------------------------------------------------------------

외부 사례에서 면접 후 회고와 팔로업 관리는 핵심 영역이다. 단순히 질문·답변을 저장하는 것을 넘어, 면접 후 개선점을 기록하고 다음 면접에 연결해야 한다.

JobFilter 적용 방향: 현재 InterviewAnswer 기능을 지원 건별 회고로 확장한다. 면접 회차, 실제 질문, 답변 자신감, 예상 밖 질문, 면접관 피드백, 다음 개선점, 회차별 회고를 추가한다. 음성 AI 모의 면접보다 비용과 개인정보 위험이 낮은 텍스트 기반 회고부터 구현한다.

================================================================================
8. 리스크와 운영 고려사항
================================================================================

JobFilter는 기능 범위가 넓어졌지만, 운영 안정성과 보안·개인정보 보호를 먼저 확보하지 않으면 확장할수록 위험이 커진다. 발표에서도 이런 리스크를 투명하게 언급해야 한다.

--------------------------------------------------------------------------------
8-1. migration과 DB 적용
--------------------------------------------------------------------------------

Experience 모델 migration이 추가됐지만, 운영 DB에 실제로 적용됐는지는 아직 확인하지 않았다. prisma/schema.prisma와 generated Prisma 파일이 작업 과정에서 자주 변경되고, generated 파일을 수동 편집하면 다음 generate에서 사라질 수 있다.

조치: schema.prisma를 유일한 모델 정의 원본으로 유지하고, migration은 prisma migrate deploy로 적용한다. migration 적용 전 DATABASE_URL와 DIRECT_URL 대상을 확인하고, 운영 DB backup과 migration rollback 방법을 문서화한다.

--------------------------------------------------------------------------------
8-2. 보안과 개인정보
--------------------------------------------------------------------------------

- API마다 세션·role·userId 소유권을 확인해야 한다. 클라이언트에서 버튼을 숨기는 것만으로 보안을 대신하지 않는다.
- 일부 API에서 User 객체 전체를 반환하거나 password·email·companyDesc 등 불필요한 개인정보를 포함할 수 있다. 모든 API select를 명시하고 DTO 변환 함수를 사용한다.
- 리크루터는 승인된 계정만 공고를 변경할 수 있어야 한다. 학생 탐색 기능은 공개 동의·마스킹·수락/거절 정책을 전제로 향후 구현한다.
- GitHub 외부 요청은 공개 저장소만 허용하고, URL protocol·도메인·timeout·응답 크기·redirect를 제한한다. 비공개 저장소 접근과 무단 분석을 금지한다.

--------------------------------------------------------------------------------
8-3. rate limit 운영
--------------------------------------------------------------------------------

현재 메모리 기반 rate limiter는 Vercel 다중 인스턴스 환경에서 전역 제한이 아니다. 공개 구인·리크루터 가입 API에는 rate limit을 적용했지만, 운영형 rate limit(KV/Redis) 전환이 필요하다.

GitHub API 공개 repo 기준 60회/시간 rate limit과 7일 캐싱 정책을 고려해야 한다. Vercel Cron 기반 공고 변경 감지도 호출 빈도와 대상 수를 제한해야 한다.

--------------------------------------------------------------------------------
8-4. E2E 검증과 테스트
--------------------------------------------------------------------------------

현재 6개의 기본 단위 테스트가 통과하지만, 실제 API Route와 세션·DB를 연결한 통합 테스트, 핵심 사용자 흐름 E2E 검증은 부족하다.

필수 E2E 흐름:
- 공고 발견 → 북마크 → 지원 등록 → Command Center → 자소서 작성·분석 → 버전 저장 → 면접 답변 → 일정 등록
- 관리자 업로드 dry-run → 선택 등록
- 리크루터 승인 → 공고 등록 → 관리자 검토 → 노출
- 타 사용자 데이터 접근 차단 401/403/404

테스트 추가 대상:
- matching.ts 점수·근거 계산
- cover-letter-analysis.ts 11개 규칙
- cover-letter-duplicate.ts 유사도
- checklist 진행률
- API 권한(비로그인 401, 타 사용자 403/404, 미승인 리크루터 403)

--------------------------------------------------------------------------------
8-5. Git 상태와 산출물 정리
--------------------------------------------------------------------------------

현재 Git 작업 트리에 추적 파일 수정사항이 많고, Prisma generated 임시 파일, 발표·분석 산출물, reports가 제품 소스와 섞여 있다.

조치:
- 발표·분석 TXT를 docs/presentation, docs/plans, docs/analysis로 이동
- reports를 docs/archive/reports로 이동
- Prisma query-engine tmp 파일은 prisma generate 후 재생성 여부 확인하고 삭제 또는 .gitignore 처리
- 사용처 없는 유틸·컴포넌트는 사용처 검색 → build 확인 → 제거
- README 현재 기능 갱신

--------------------------------------------------------------------------------

화면: 지원 건 카드 중심에 자소서·면접·포트폴리오·일정 연결
원고: 지원 공고 상세가 단순한 정보 페이지에서 준비 워크스페이스로 바뀌었습니다. 아직 포트폴리오와 면접 답변의 직접 연결은 향후 계획입니다.

--------------------------------------------------------------------------------
SLIDE 07. 지원 준비율과 대시보드
--------------------------------------------------------------------------------

화면: 준비율 75% (자소서·체크리스트·면접일·팔로업 4개 항목)
원고: 지원 건마다 어떤 준비가 남았는지 한눈에 봅니다. 대시보드에는 우선순위 공고와 오늘의 할 일 1차가 표시됩니다. 별도 /today 페이지는 현재 구현하지 않았습니다.

--------------------------------------------------------------------------------
SLIDE 08. 룰 기반 자소서 코칭
--------------------------------------------------------------------------------

화면: 분량·수치·STAR·직군 키워드·문장 길이·공허한 표현 분석
원고: AI API 없이 11개 항목을 룰 기반으로 분석합니다. 외부 AI 비용 없이 1차 피드백을 주지만, 문맥 이해에는 한계가 있어 작성 보조 피드백으로 제공합니다.

--------------------------------------------------------------------------------
SLIDE 09. 피드백 하이라이트·버전 diff
--------------------------------------------------------------------------------

화면: 피드백 클릭 → 문항 이동 → 하이라이트 / 두 버전 diff 비교
원고: 피드백을 보고 다시 문장을 찾지 않아도 됩니다. 버전 diff로 수정 전후를 직접 비교할 수 있습니다.

--------------------------------------------------------------------------------
SLIDE 10. STAR 기반 경험 저장소
--------------------------------------------------------------------------------

화면: 상황·행동·결과·기술·성과 구조화 입력 → 자소서 문항 삽입
원고: 한 번 기록한 경험을 여러 자소서와 면접 준비에 재사용합니다.

--------------------------------------------------------------------------------
SLIDE 11. 관리자 dry-run 업로드
--------------------------------------------------------------------------------

화면: Excel 업로드 → preview → 포함/제외/중복/파싱 실패 통계 → 선택 등록
원고: 잘못된 Excel이 그대로 DB에 들어가는 것을 막습니다. 10MB, 5,000행 제한, 컬럼 매핑, IT·개발 필터, 중복 예상, dry-run 후 선택 등록을 지원합니다.

--------------------------------------------------------------------------------
SLIDE 12. 리크루터·API 보안
--------------------------------------------------------------------------------

화면: Client → Server Firewall → Database, 로그인·role·소유권·schema 검증
원고: 리크루터는 관리자 승인 후 공고를 등록하고, 수정 시 재검토 상태가 됩니다. Zod 입력 검증, URL·날짜 검증, rate limit을 적용했습니다.

--------------------------------------------------------------------------------
SLIDE 13. 현재 상태와 한계
--------------------------------------------------------------------------------

화면: 현재 구현 / 1차 구현 / 향후 계획 색상 구분
원고: 핵심 흐름은 구현됐지만, 포트폴리오·면접 직접 연결, 전체 API 권한 테스트, 운영 DB migration 적용 확인, 전체 DTO 정리가 남아 있습니다.

--------------------------------------------------------------------------------
SLIDE 14. 다음 개발 우선순위
--------------------------------------------------------------------------------

화면: P0·P1·Hold 로드맵
원고: 먼저 API 권한·migration·DTO·알림 구조화·업로드 안정성을 확보하고, 그 다음 지원 준비 리포트·오늘의 할 일·기술 증거 매핑을 구현합니다.

--------------------------------------------------------------------------------
SLIDE 15. 최종 기대 효과
--------------------------------------------------------------------------------

화면: 취업 준비 End-to-End 플랫폼
원고: JobFilter의 목표는 기능을 많이 추가하는 것이 아니라, 학생이 공고를 발견한 뒤 하나의 지원 건을 중심으로 취업 준비 전체 과정을 끊김 없이 관리하도록 만드는 것입니다.

--------------------------------------------------------------------------------
시연 주의사항
--------------------------------------------------------------------------------

- 실제 이메일·비밀번호·연락처를 노출하지 않는다.
- DB 연결 화면은 테스트 계정으로 준비한다.
- 네트워크 오류 대비 캡처를 준비한다.
- 실제 구현과 향후 계획을 구분한다.
- 별도 /today 페이지를 시연하지 않는다.

================================================================================
11. 결론
================================================================================

JobFilter는 공고를 많이 보여주는 서비스에서, 학생이 하나의 지원 건을 중심으로 취업 준비를 이어갈 수 있는 서비스로 발전하고 있다.

현재까지의 핵심 변화는 다음과 같다.

- 공고 매칭을 설명 가능하게 만들어 일치 기술·부족 기술·적합 근거를 함께 보여준다.
- 지원 건 Command Center를 추가해 자소서·면접·포트폴리오·일정으로 빠르게 이동할 수 있게 했다.
- 지원 준비율 1차를 표시해 자소서·체크리스트·면접·팔로업 준비 상태를 한눈에 볼 수 있게 했다.
- 자소서 분석을 실제 문장 수정과 연결해 피드백 → 하이라이트 → 수정 → 재분석 흐름을 만들었다.
- 버전 diff로 수정 전후를 비교할 수 있게 했다.
- 경험 저장소로 STAR 경험을 재사용할 수 있게 했다.
- 알림 조회와 생성 시점을 분리해 GET 요청 부작용을 제거했다.
- 관리자 Excel 공고 업로드를 dry-run으로 안전하게 만들었다.
- 리크루터·공개 구인 API의 입력과 요청을 제한했다.

앞으로는 기능을 더 추가하기보다 다음을 강화해야 한다.

- 실제 API 통합 권한 테스트, 운영 DB migration 적용 확인, 전체 API DTO 정리
- 포트폴리오·면접 답변의 지원 건 직접 연결
- 로드맵과 공고 기술 연결, 기술 증거 매핑
- 회사·공고 조사 노트, 지원 활동 분석, 면접 회고
- 리크루터 학생 탐색과 공개 동의 세분화

발표에서 가장 강조해야 할 문장은 다음과 같다.

“JobFilter의 핵심은 기능을 많이 나열하는 것이 아닙니다. 학생이 공고를 발견한 뒤 하나의 지원 건을 중심으로 자소서·경험·면접·포트폴리오·일정을 준비하고, 그 결과를 기록할 수 있도록 연결하는 것입니다. 현재는 그 통합 흐름의 1차 기반을 구현했고, 앞으로 데이터 직접 연결과 운영 안정성을 강화할 계획입니다.”
