================================================================================
JobFilter 전체 작업 보고서 및 발표용 설명 자료
================================================================================

작성일: 2026-08-10
프로젝트: JobFilter
대상 학과: 컴퓨터정보과·인공지능소프트웨어과
기술 스택: Next.js 14, React, TypeScript, Prisma, PostgreSQL, NextAuth, Vercel

이 문서의 목적
- 지금까지 JobFilter에 실제로 반영한 작업을 발표자가 설명할 수 있도록 정리한다.
- 무엇을 만들었는지뿐 아니라 왜 만들었는지, 기존 문제는 무엇이었는지, 어떤 방식으로 해결했는지 설명한다.
- 현재 구현과 앞으로 남은 계획을 구분한다.

발표 핵심 메시지
JobFilter는 단순 채용공고 목록이 아니라,
공고 발견 → 지원 등록 → 자소서·포트폴리오·면접 준비 → 일정 관리 → 결과 분석을
하나의 지원 건 중심으로 연결하는 취업 준비 플랫폼이다.

중요 구현 원칙
- 외부 AI API 없이 룰 기반 분석을 우선한다.
- 기능을 늘리기 전에 기존 기능을 연결한다.
- 사용자의 데이터는 userId와 서버 소유권 검증으로 보호한다.
- 관리자와 리크루터의 역할을 서버에서 검사한다.
- 삭제·이동 작업은 Git 변경사항 보존과 사용처 확인 후 진행한다.
- 운영 DB에 영향을 주는 migration은 별도 확인 후 적용한다.

1. 작업 시작 전 문제 분석
================================================================================

기존 문제

1. 공고와 준비 기능이 분리되어 있었다.
- 사용자는 공고를 찾은 뒤 자소서, 체크리스트, 면접, 포트폴리오 화면을 따로 방문해야 했다.
- 지원 하나를 준비하는 과정이 여러 페이지에 흩어졌다.

2. 매칭 점수의 근거가 부족했다.
- “매칭 72%” 같은 숫자만으로는 왜 적합한지 알기 어려웠다.
- 목록과 대시보드에서 계산 기준이 달라질 가능성이 있었다.

3. 알림 생성에 조회 부작용이 있었다.
- GET /api/jobs 조회 시 알림을 생성했다.
- 목록을 새로고침할 때마다 DB 조회·쓰기와 중복 확인이 발생할 수 있었다.

4. 관리자 공고 업로드의 검증이 부족했다.
- 파일 크기와 행 수 제한이 필요했다.
- 등록 전에 중복·파싱 실패·제외 행을 확인하기 어려웠다.

5. 리크루터·공개 구인 API의 입력 검증이 부족했다.
- 회사명과 직무 외의 필드가 일관되게 검증되지 않았다.
- URL, 날짜, 이메일, 문자열 길이 제한이 필요했다.

6. 자소서 기능의 분석 결과와 실제 수정 화면 연결이 약했다.
- 분석 결과를 읽은 뒤 직접 어느 문장을 고쳐야 하는지 다시 찾아야 했다.

7. 경험이 자소서마다 반복 입력되었다.
- 상황·행동·결과·기술·성과를 구조화해서 저장할 공간이 없었다.

8. 버전 히스토리는 있었지만 비교가 부족했다.
- 과거 버전으로 복원할 수는 있었지만 두 버전의 내용 차이를 한눈에 확인하기 어려웠다.

9. 지원 건별 준비 상태를 종합적으로 볼 수 없었다.
- 자소서 연결, 체크리스트, 일정 상태를 한 번에 판단하기 어려웠다.

3. 매칭 점수 통합 및 설명 가능성 개선
================================================================================

대상 파일
- lib/matching.ts
- lib/matching.test.ts
- app/api/listings/route.ts
- app/api/dashboard/priority-jobs/route.ts

기존 문제
- 공고 목록에서 계산하는 점수와 대시보드 우선순위 계산이 서로 달랐다.
- 직무명과 태그를 단순 교집합으로 처리했다.
- 점수만 표시되고 일치·부족 기술이 표시되지 않았다.

구현한 내용
- 공통 matching 모듈을 만들었다.
- 사용자 기술과 공고 태그를 비교한다.
- 일치 기술을 반환한다.
- 사용자가 보유하지 않은 공고 기술을 부족 기술로 반환한다.
- 목표 직무와 공고 직무의 유사도를 계산한다.
- 신입·무관·인턴 조건을 참고한다.
- 마감 긴급도를 계산한다.
- 최종 점수와 계산 근거를 함께 반환한다.

점수 구성 방향
- 기술 일치: 가장 큰 비중
- 직무 적합
- 경력 조건
- 마감 긴급도

왜 이렇게 했는가
- 숫자만 보여주면 사용자가 점수를 신뢰하기 어렵다.
- “왜 적합한가?”와 “무엇을 더 준비해야 하는가?”를 동시에 알려줘야 한다.
- 목록과 대시보드의 기준을 통합해야 사용자 혼란을 줄일 수 있다.

화면 결과
- 매칭 점수
- 일치 기술
- 부족 기술
- 목표 직무와 유사 여부
- 신입 지원 가능 여부
- 마감 임박 여부

주의
- 이 점수는 합격 가능성 예측이 아니다.
- 사용자 기술과 공고 요구사항을 비교한 참고 지표다.

검증
- matching.test.ts에서 일치 기술·부족 기술·프로필 없음 케이스를 검증했다.

4. 지원 건 Command Center와 준비 리포트
================================================================================

대상 파일
- app/(dashboard)/jobs/[id]/page.tsx
- app/api/jobs/[id]/route.ts

기존 문제
- 지원 공고 상세, 자소서, 면접, 포트폴리오, 일정이 분리되어 있었다.
- 지원 하나를 준비하려면 여러 페이지를 이동해야 했다.

구현한 내용
- 지원 건 상세에 지원 준비 워크스페이스를 추가했다.
- 자소서 준비 화면으로 이동한다.
- 면접 연습 화면으로 이동한다.
- 포트폴리오 화면으로 이동한다.
- 일정 관리 화면으로 이동한다.
- 지원 건에서 자소서 화면으로 이동할 때 jobId를 전달한다.

1차 준비 리포트
- 지원 준비율을 표시한다.
- 자소서 연결 여부를 표시한다.
- 체크리스트 전체 완료 여부를 표시한다.
- 면접 일정 설정 여부를 표시한다.
- 팔로업 일정 설정 여부를 표시한다.
- 최근 연결 자소서 분석 점수를 표시한다.

준비율 계산
- 자소서 연결
- 체크리스트 전체 완료
- 면접 일정 설정
- 팔로업 일정 설정

각 항목을 1개씩 계산해 0~100%로 표시한다.

왜 이렇게 했는가
- JobFilter의 중심을 공고가 아니라 지원 건으로 바꾸기 위해서다.
- 사용자가 지금 무엇이 준비됐고 무엇이 비어 있는지 즉시 확인할 수 있다.
- 기존 데이터와 기능을 재사용하므로 새 기능을 과도하게 만들지 않는다.

API 개선
- 지원 건을 조회할 때 userId 조건을 함께 사용한다.
- 연결된 자소서는 원문 전체가 아니라 id·version·analysisScore·updatedAt만 조회한다.
- 지원 건 소유자가 아닌 사용자는 접근할 수 없다.

현재 한계
- 포트폴리오와 면접 답변의 실제 개수는 아직 지원 건에 직접 연결하지 않았다.
- 다음 단계에서 Portfolio·InterviewAnswer와 연결할 예정이다.

5. 자소서 룰 기반 코칭 강화
================================================================================

- lib/cover-letter-analysis.ts

기존 기능
- 분량
- 공허한 표현
- 수치 포함 여부
- STAR 구조
- 직군 키워드
- 긴 문장
- 협업 표현
- 첫 문장 패턴
- 접속사 반복
- 수동태
- 추상적 표현
- 버전 히스토리
- 점수 변화 그래프
- JD 키워드 히트맵
- 자소서 중복 검사

추가 구현: 피드백 클릭 이동·하이라이트

동작
1. 코칭 분석을 실행한다.
2. 경고 또는 오류 피드백을 클릭한다.
3. 피드백 메시지의 따옴표 표현을 찾는다.
4. 첫 문장·접속사·수동태·추상 표현은 알려진 후보 표현을 찾는다.
5. 해당 자소서 문항을 자동으로 펼친다.
6. 해당 문항으로 스크롤한다.
7. 문제 표현을 하이라이트한다.

왜 이렇게 했는가
- 분석 결과만 읽고 끝나면 실제 개선 행동으로 연결되지 않는다.
- 피드백과 편집 위치 사이의 이동을 줄여야 한다.
- 외부 AI 없이도 규칙 기반 분석 결과를 편집 흐름에 연결할 수 있다.

룰 기반 방식의 이유
- 무료 학생 서비스에서 API 비용을 낮춘다.
- 분량·문장 길이·키워드·수치·STAR 같은 1차 점검은 정규식과 키워드로 가능하다.
- 단, 문맥 이해의 한계가 있으므로 합격 판정이 아니라 작성 보조로 안내한다.

6. 자소서 버전 diff
================================================================================

대상 파일
- app/(dashboard)/cover-letter/page.tsx
- app/api/cover-letter/[id]/versions/route.ts

구현한 내용

- 선택한 버전의 문항을 비교한다.
- 변경된 문항 수를 표시한다.
- 이전 답변을 빨간색 영역으로 표시한다.
- 변경 답변을 초록색 영역으로 표시한다.
- 동일한 경우 변경 없음으로 표시한다.
- 기존 복원 기능은 유지한다.

왜 이렇게 했는가
- 점수 그래프만으로는 무엇을 고쳤는지 알기 어렵다.
- 사용자가 수정 전후 문장을 직접 비교해야 개선 과정을 이해할 수 있다.
- 버전 복원과 diff 비교를 함께 제공하면 실험적인 수정도 안전하게 할 수 있다.

데이터 구조
- title: 경험 제목

API
- GET /api/experiences
- POST /api/experiences
- PATCH /api/experiences/:id
- DELETE /api/experiences/:id

보안
- 조회 시 userId 조건 사용
- 수정 전 id와 userId 함께 조회
- 삭제는 deleteMany에 id와 userId를 함께 사용
- 타 사용자 경험 ID 접근을 차단한다.
- API 응답에서 userId를 제외한 명시적 DTO를 사용한다.

화면
- 자소서 작성 SlideOver 안에 경험 저장소 표시
- 새 경험 저장
- 저장 경험 목록
- 경험 삭제
- 경험 삽입
- 상황·행동·결과·기술·성과를 답변 형태로 조합

왜 이렇게 했는가
- 같은 프로젝트 경험을 자소서마다 반복 입력하지 않게 한다.
- STAR 구조로 저장하면 자소서·면접·포트폴리오에서 재사용할 수 있다.
- AI 생성 없이 구조화된 사용자 데이터를 활용한다.

Migration 주의
- schema.prisma만 변경한다고 운영 DB에 자동 반영되는 것은 아니다.
- prisma migrate deploy로 대상 DB에 적용해야 한다.
- 운영 DB 적용 전 backup·환경변수·migration status 확인이 필요하다.

대상 파일

기존 문제
- GET /api/jobs 조회 시 알림을 생성했다.
- 조회만 해도 DB 쓰기가 발생했다.
- 문자열 body 검색으로 중복을 확인했다.

구현한 내용
- GET /api/jobs에서는 조회만 수행한다.
- POST /api/notifications/sync에서 알림을 동기화한다.
- 마감 임박 알림을 생성한다.
- 면접 일정 알림을 생성한다.
- 14일 이상 경과한 지원 건 팔로업 알림을 생성한다.
- 알림 페이지에서 동기화 후 목록을 조회한다.

대시보드 오늘의 할 일
- 마감 준비
- 면접 준비
- 팔로업 확인
- 준비물 확인
- 긴급·일반 작업 구분
- 지원 건 상세로 이동

왜 이렇게 했는가
- GET 요청은 가능한 한 읽기 동작이어야 한다.
- 알림 생성 시점을 명시적인 sync로 분리하면 중복과 부작용을 줄일 수 있다.
- 사용자가 앱을 열었을 때 “무엇을 해야 하는가”를 바로 보여준다.

현재 한계
- 실제 완료 작업을 별도 저장하는 ApplicationTask 모델은 아직 없다.
- 지원 준비 리포트의 포트폴리오·면접 상세 연결은 추가 작업이 필요하다.

- 운영 규모가 커지면 Redis·Upstash 등 외부 저장소 기반으로 바꿔야 한다.

13. 발표에서 설명할 전체 흐름
================================================================================

1. 학생이 맞춤 공고에서 공고를 발견한다.
2. 매칭 점수와 일치·부족 기술을 확인한다.
3. 지원 목록에 추가한다.
4. 지원 건 Command Center에서 준비율을 확인한다.
5. 자소서 분석 결과를 클릭해 문제 문장으로 이동한다.
6. 경험 저장소의 STAR 경험을 자소서에 삽입한다.
7. 버전 두 개를 선택해 수정 전후를 비교한다.
8. 체크리스트·면접·일정·팔로업을 관리한다.
9. 대시보드에서 오늘의 할 일을 확인한다.
10. 지원 결과와 취업 활동을 분석한다.

발표용 핵심 답변

Q. 왜 AI를 사용하지 않았나요?
A. 학생 대상 서비스의 운영비를 줄이고, 분량·키워드·문장 길이·STAR 같은 1차 피드백을 안정적으로 제공하기 위해 룰 기반으로 구현했습니다. 문맥 판단은 제한적이므로 합격 판정이 아니라 작성 보조로 안내합니다.

Q. 매칭 점수는 합격 가능성인가요?
A. 아닙니다. 개인 기술과 공고 요구사항을 비교한 참고 지표입니다. 일치 기술·부족 기술·직무·경력·마감 근거를 함께 표시합니다.

Q. 가장 중요한 구현은 무엇인가요?
A. 지원 건 중심 연결입니다. 공고를 찾는 것보다 실제로 지원을 준비하고 완료하는 과정이 중요하기 때문입니다.

Q. 개인정보는 어떻게 보호하나요?
A. API에서 세션·역할·소유권을 서버에서 확인하고, 리크루터는 승인된 계정만 사용합니다. 학생 공개 정보는 향후 명시적 동의와 마스킹을 기준으로 제공합니다.

Q. 왜 관리자 업로드 미리보기가 필요한가요?
A. 학교 Excel에는 전공과 무관한 공고, 중복, 날짜 오류가 섞일 수 있으므로 DB에 등록하기 전에 결과를 확인해야 합니다.
