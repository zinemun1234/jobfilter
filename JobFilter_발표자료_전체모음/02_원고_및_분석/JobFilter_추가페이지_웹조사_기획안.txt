1. 현재 JobFilter 페이지 구성
================================================================================

학생용 현재 페이지
- /dashboard: 지원 현황, 우선순위 공고, 로드맵, 오늘의 할 일
- /listings: 맞춤 공고 검색·필터·매칭·북마크
- /listings/[id]: 공고 상세 및 지원 목록 추가
- /jobs: 지원 현황 테이블·칸반
- /jobs/[id]: 지원 건 상세, 체크리스트, 상태 이력, Command Center 연결
- /cover-letter: 자소서 작성, 룰 기반 코칭, 히트맵, 중복 검사, 버전 diff, 경험 저장소
- /interview: 면접 질문, 답변, 모의 면접
- /portfolio: 프로젝트 등록, GitHub 분석, PDF export
- /roadmap: 직무별 기술 학습 로드맵
- /calendar: 마감·면접·팔로업 일정
- /notifications: 알림 목록 및 읽음 처리
- /bookmarks: 공고 북마크
- /profile: 전공·목표 직무·기술 스택
- /notices: 공지사항

관리자용 현재 페이지
- 공고 관리
- Excel/CSV 업로드 및 미리보기
- 일괄 처리
- 사용자 관리
- 면접 질문 관리
- 공지 관리
- 취업 기록
- 통계

리크루터용 현재 페이지
- 리크루터 공고 등록·수정·삭제
- 관리자 승인 기반 공고 노출 흐름

현재 판단
- 학생 핵심 기능은 이미 충분히 많다.
- 새 페이지는 단순히 메뉴 수를 늘리는 방향보다 기존 지원 건과 데이터를 연결해야 한다.
- 가장 효과적인 추가 페이지는 지원 준비 완료율, 증거 기반 포트폴리오, 활동 분석, 학교 지원 연결 페이지다.

2. 웹 조사에서 확인한 반복 기능
================================================================================

2-1. 지원 추적·애플리케이션 관리

Apply Tracker 조사 내용
- 애플리케이션을 Kanban 보드로 관리
- Applied, Interviewing, Offer Received 같은 단계 관리
- 인터뷰 리마인더
- 제안 조건 기록 및 비교
- 응답 시간·전환율·지원 퍼널 분석
- ATS 이력서 검사
- 커버레터와 이력서 관리

JobFilter 적용 시사점
- 기본 상태 관리는 이미 있으므로 단순 Kanban 추가는 차별성이 낮다.
- 대신 지원 건별 준비율, 상태별 전환율, 제안 비교처럼 현재 데이터와 연결되는 기능이 우선이다.

2-2. 학생용 취업 준비 워크스페이스

Notion 학생 취업 추적 템플릿 조사 내용
- 지원 상태 추적
- 회사 데이터베이스
- 관심 인물·네트워킹 연락처 관리
- 포트폴리오·CV·자소서 자료 관리
- 개인 대시보드 형태의 통합 관리

JobFilter 적용 시사점
- 지원 건 Command Center 방향이 타당하다.
- 담당자 연락처와 팔로업 날짜를 이미 보유하고 있으므로 네트워킹 페이지로 확장할 기반이 있다.
- 다만 소셜 네트워크 기능을 새로 만들기보다 지원 건의 담당자·후속 연락 관리에 집중한다.

2-3. 대학 커리어 서비스 플랫폼

VIAS Career Services 조사 내용
- 학생의 취업 진행 상황 관리
- 공고 및 이력서 검토
- 취업 박람회·네트워킹 이벤트
- 기업 관계 및 연락처 관리
- 취업 결과 보고서와 분석

JobFilter 적용 시사점
- 관리자용 학생 취업 지원 페이지가 유용하다.
- 학교 운영자는 공고 수보다 학생이 어느 단계에서 막히는지 확인해야 한다.
- 개인정보를 최소화한 집계형 통계부터 제공해야 한다.

2-4. ATS·직무 준비

검색 결과와 Apply Tracker 조사 내용
- ATS 구조·헤딩·연락처·키워드·문서 형식 점검
- 공고와 이력서·자소서의 키워드 비교
- 약한 부분과 개선 방향 제공
- 직무별 이력서·면접 질문·회사 리뷰 자료 연결

JobFilter 적용 시사점
- 현재 자소서 룰 기반 코칭과 JD 히트맵은 좋은 기반이다.
- 다음에는 자소서만 점수화하지 말고 지원 건의 “준비 증거”를 보여주는 것이 좋다.
- 자동 합격 예측이나 AI 대필이 아니라 체크 가능한 근거 중심으로 유지한다.

P0. 지원 준비 리포트 페이지

추천 경로
- /jobs/[id]/readiness 또는 Command Center 내부 탭

목적
- 특정 지원 건이 실제 제출 가능한 상태인지 한눈에 확인한다.

화면 구성
- 지원 상태 및 D-Day
- 준비율
- 자소서 연결 여부
- 자소서 최근 분석 점수
- 포트폴리오 연결 여부
- 대표 프로젝트
- 체크리스트 완료율
- 면접 질문 답변 수
- 담당자·팔로업 일정
- 부족한 준비 항목
- 다음 행동 1개

기존 데이터 활용
- JobPosting
- CoverLetter
- Experience
- Portfolio
- InterviewAnswer
- checklist
- followUpAt

우선순위: P0
구현 난이도: 중간
개인정보 위험: 낮음
추천 이유
- 새 데이터 수집 없이 현재 기능을 묶어 사용자 가치가 가장 크게 증가한다.
- JobFilter의 핵심 메시지인 “공고 탐색을 취업 준비로 연결”하는 대표 페이지가 된다.

완료 기준
[ ] 지원 건 하나를 선택하면 준비 상태를 한 화면에서 확인한다.
[ ] 부족한 항목을 클릭하면 해당 페이지로 이동한다.
[ ] 준비율 계산 기준이 화면에 표시된다.

추천 경로
- /tasks 또는 /today

목적
- 대시보드에 표시된 할 일을 날짜·지원 건·우선순위별로 관리한다.

화면 구성
- 오늘·내일·이번 주 탭
- 마감 임박
- 면접 준비
- 팔로업
- 체크리스트
- 자소서 수정
- 완료 처리
- 지원 건으로 이동
- 일정 생성·변경

기존 데이터 활용
- JobPosting deadline/interviewAt/followUpAt
- JobPosting checklist
- UserNotification

우선순위: P0
구현 난이도: 낮음~중간
개인정보 위험: 낮음
추천 이유
- 현재 대시보드의 오늘의 할 일을 확장하면 되므로 중복 구현이 적다.
- 사용자가 앱을 열고 무엇을 해야 할지 바로 결정할 수 있다.

주의
- GET 요청에서 알림이나 작업을 생성하지 않는다.
- 완료 상태는 중복 생성되지 않도록 별도 식별자를 사용한다.

주의

- 최소 표본 수 미만의 통계는 숨기거나 “참고용”으로 표시한다.
- 관리자 화면에서는 학생 개인을 식별할 수 없게 집계한다.

P3. 공고 변경 비교 페이지

추천 경로
- /jobs/[id]/changes

목적
- 원문 공고의 변경 내용을 확인한다.

화면 구성
- 마지막 확인일
- 변경된 마감일
- 변경된 자격요건
- 변경된 기술 키워드
- 변경 전·후 비교
- 확인 후 상태 처리

우선순위: P3
구현 난이도: 높음
개인정보 위험: 낮음
운영 위험: 높음

1차 구현 원칙
- 자동 크롤링부터 시작하지 않는다.
- 사용자가 “지금 확인”을 눌렀을 때 허용된 원문 URL만 확인한다.
- 요청 timeout·도메인 제한·rate limit을 적용한다.
- 원문 제공자의 이용약관을 확인한다.

4. 추천하지 않는 추가 페이지
================================================================================

당장 추가하지 않을 페이지

- 커뮤니티 피드
- 학생 간 팔로우·좋아요
- AI 자기소개서 자동 생성 페이지
- 음성 기반 AI 면접 페이지
- 무제한 채용 사이트 크롤링 페이지
- 의미 없이 차트만 보여주는 통계 페이지
- 공개 동의 없는 학생 검색 페이지

이유
- 핵심 취업 준비 흐름과 직접 연결되지 않는다.
- 운영비·관리 비용이 크다.
- 개인정보와 콘텐츠 품질 위험이 커진다.
- 현재 P0·P1 기능이 해결되지 않은 상태에서 기능이 분산된다.

5. 최종 추천 구현 순서
================================================================================

1단계: 지원 준비 리포트
- 기존 Command Center 내부 탭으로 먼저 구현
- 준비율·누락 항목·다음 행동을 통합

2단계: 오늘의 할 일 상세 페이지
- 대시보드의 할 일 로직을 재사용
- 완료·날짜 변경·지원 건 이동 추가

3단계: 기술 증거·포트폴리오 매핑
- Experience, Portfolio, Roadmap, Matching 연결
- 부족 기술을 증거 부족 기술로 전환

4단계: 회사·공고 조사 노트
- 외부 크롤링 없이 사용자 메모 기반으로 시작
- 자소서·면접과 연결

5단계: 지원 활동 분석
- 개인 통계부터 시작
- 충분한 데이터가 쌓인 뒤 관리자 익명 집계 추가

6단계: 면접 회고
- 질문·답변 저장에 회차·피드백·개선점 추가

7단계: 학교 상담·리크루터 확장
- 권한·동의·운영 정책을 확정한 뒤 구현

6. 페이지 추가 판단 기준
================================================================================

새 페이지를 만들기 전에 확인할 질문

[ ] 기존 페이지 안의 탭이나 섹션으로 해결할 수 없는가?
[ ] 특정 지원 건 또는 사용자 목표와 연결되는가?
[ ] 기존 DB 데이터로 1차 구현할 수 있는가?
[ ] 사용자가 다음 행동을 바로 할 수 있는가?
[ ] 완료율·전환율 등 성공 지표를 측정할 수 있는가?
[ ] 개인정보 공개 범위가 명확한가?
[ ] 외부 API·크롤링·운영비가 통제되는가?
[ ] 모바일에서 핵심 행동이 가능한가?
[ ] 빈 데이터 상태를 안내할 수 있는가?
[ ] 관련 API의 소유권·역할 검증을 테스트할 수 있는가?

원칙
- P0는 기존 페이지 내부 연결을 먼저 시도한다.
- 새 URL은 사용자 행동이 명확하게 달라질 때만 만든다.
- 모든 페이지에는 빈 상태, 오류 상태, 로딩 상태가 있어야 한다.
- 페이지 수보다 사용자 여정 완성도를 우선한다.

8. 결론
================================================================================

추가 페이지를 많이 만드는 것보다 다음 3개를 우선한다.

1. 지원 준비 리포트
2. 오늘의 할 일 상세
3. 기술 증거·포트폴리오 매핑

이 세 가지는 기존 기능을 재사용하면서도 JobFilter의 차별점인
“공고 발견부터 취업 준비 증거와 결과 분석까지 연결”을 가장 분명하게 만든다.

최종 추천
- 먼저 Command Center 내부 탭으로 지원 준비 리포트를 만든다.
- 독립 페이지는 오늘의 할 일과 분석처럼 반복 방문이 필요한 기능부터 만든다.
- 리크루터 학생 탐색과 학교 상담은 개인정보·운영 정책을 확정한 뒤 진행한다.
