이 글을 쓰는 이유

기존 자료들은 기능과 계획을 잘 정리하고 있지만,
발표할 때 그대로 읽으면 조금 딱딱하고 기능 목록처럼 들릴 수 있다.
그래서 이 문서는 실제 프로젝트를 진행한 사람이 설명하는 것처럼,
무엇을 만들었고 왜 만들었으며 앞으로 무엇을 보완해야 하는지를 자연스럽게 정리한 문서다.

발표에서 지켜야 할 기준

- 실제로 구현된 기능은 구현됐다고 말한다.
- 일부만 연결된 기능은 1차 구현이라고 말한다.
- 아직 기획 단계인 기능은 향후 계획으로 분명히 말한다.
- 화면에 버튼이 있는 것과 실제 데이터가 완전히 연결된 것은 구분한다.
- migration 파일이 있는 것과 운영 DB에 적용된 것은 구분한다.
- 단위 테스트 통과와 실제 사용자 E2E 검증은 구분한다.

================================================================================
1. JobFilter를 만들게 된 배경
================================================================================

학생 입장에서 취업 준비를 시작하면 가장 먼저 공고를 찾아야 한다.
그런데 학교에서 받는 공고 파일은 학생이 바로 사용하기에 불편한 경우가 많다.
개발직과 사무직이 섞여 있고, 회사명이나 직무명이 일정하지 않은 경우도 있다.

공고를 하나 찾았다고 해서 준비가 끝나는 것도 아니다.
그다음에는 자소서를 써야 하고, 포트폴리오를 정리해야 하고,
면접 질문을 준비하고, 마감일과 면접일도 기억해야 한다.

이 자료들이 각각 다른 화면이나 메모에 흩어져 있으면
학생은 계속 같은 정보를 다시 입력하게 된다.
지원한 회사가 어디인지, 자소서를 만들었는지,
체크리스트를 끝냈는지, 면접 준비를 했는지 한 번에 보기 어렵다.

JobFilter는 이 불편함을 줄이기 위해 시작했다.
처음에는 학과에 맞는 공고를 찾는 서비스였지만,
개발을 진행하면서 공고를 찾는 것보다 그 이후의 준비 과정을 연결하는 것이 더 중요하다는 판단을 했다.

그래서 현재 JobFilter의 중심은 공고 목록 자체가 아니라
“지원 건 하나를 끝까지 준비할 수 있는가”에 있다.

================================================================================
2. 현재 서비스가 해결하는 문제
================================================================================

첫 번째 문제는 공고가 너무 많고 섞여 있다는 것이다.

관리자가 Excel이나 CSV를 업로드하면 시스템은 회사명·직무·지역 등 컬럼을 매핑하고,
IT·개발 관련 키워드를 기준으로 학생에게 적합한 공고를 먼저 걸러낸다.
관리자는 등록 전에 어떤 행이 파싱됐고, 어떤 행이 제외됐고,
어떤 공고가 중복인지 미리 확인할 수 있다.

두 번째 문제는 공고가 나에게 맞는지 판단하기 어렵다는 것이다.

JobFilter는 사용자 기술 스택과 공고의 기술 tags를 비교한다.
단순히 매칭 숫자만 보여주는 것이 아니라,
일치 기술과 부족 기술을 함께 보여준다.
그래서 학생은 “이 공고가 나에게 맞는가?”뿐 아니라
“지원하기 전에 무엇을 더 준비해야 하는가?”도 알 수 있다.

세 번째 문제는 지원 준비가 여러 화면으로 흩어진다는 것이다.

지원 건 상세에 Command Center를 추가해
자소서·면접·포트폴리오·일정 화면으로 바로 이동하게 했다.
준비율 1차도 추가해 자소서 연결, 체크리스트, 면접 일정, 팔로업 일정을 한 번에 확인하게 했다.

네 번째 문제는 자소서의 부족한 부분을 찾기 어렵다는 것이다.

외부 AI를 사용하지 않고도 분량, 수치, STAR 구조,
공허한 표현, 긴 문장, 접속사 반복 등을 규칙 기반으로 분석한다.
분석 결과를 클릭하면 실제 문제 문장으로 이동하고 하이라이트한다.

다섯 번째 문제는 경험을 계속 반복해서 쓰는 것이다.

경험 저장소에 상황·행동·결과·사용 기술·성과를 저장하고,
필요할 때 자소서 문항에 삽입할 수 있도록 했다.

================================================================================
3. 현재 구현된 기능을 사람의 관점에서 설명하면
================================================================================

3-1. 맞춤 공고 탐색

관련 화면
- /listings
- /listings/[id]

학생이 할 수 있는 일

- 회사명·직무·지역으로 검색
- 마감 임박 공고만 보기
- 7일 이내 마감 공고 보기
- 신입·경력 조건 필터링
- 자신의 기술 스택 기준 매칭순 정렬
- 공고 북마크
- 내 지원 목록 추가
- 공고에서 자소서 작성 화면으로 이동

실제 사용 장면

학생이 React와 TypeScript를 프로필에 저장해두었다고 하자.
공고에 React가 필요하면 매칭 결과에 일치 기술로 표시된다.
공고에 Docker와 AWS가 있는데 학생이 아직 갖고 있지 않다면 부족 기술로 표시된다.

왜 이렇게 만들었는가

학생이 모든 공고를 처음부터 끝까지 읽는 것은 현실적으로 어렵다.
먼저 자신과 관련 있는 공고를 좁혀주면 검색에 드는 시간을 줄일 수 있다.
하지만 자동 필터가 학생의 판단을 대신하면 안 되므로,
최종 선택은 학생이 하되 판단에 필요한 근거를 제공하는 방향으로 만들었다.

현재 한계

- 기술 이름의 동의어나 의미까지 완전히 이해하는 것은 아니다.
- 공고 tags가 잘못 추출되면 매칭 결과도 영향을 받는다.
- 대량 공고에 대한 서버 페이지네이션과 검색 최적화는 추가로 필요하다.

3-2. 설명 가능한 매칭 점수

관련 파일
- lib/matching.ts
- app/api/listings/route.ts
- app/api/dashboard/priority-jobs/route.ts
- lib/matching.test.ts

이 기능을 만들기 전에는 목록과 대시보드가 서로 다른 기준으로 점수를 계산할 가능성이 있었다.
그래서 매칭 계산을 공통 함수 하나로 모았다.

계산하는 항목

- 기술 일치
- 직무 유사도
- 경력 조건
- 마감 긴급도

반환하는 정보

- 전체 점수
- 일치 기술
- 부족 기술
- 적합 근거

왜 이렇게 만들었는가

“매칭 72%”라는 숫자만 보여주면 학생은 그 숫자를 믿을 이유가 없다.
오히려 점수가 낮을 때 무엇이 부족한지도 알려줘야 준비 방향이 생긴다.

발표에서는 반드시 이렇게 설명한다.

“이 점수는 합격 가능성을 예측하는 점수가 아닙니다.
학생의 기술과 공고의 요구사항을 비교한 참고 지표입니다.”

3-3. 지원 현황 관리

관련 화면
- /jobs
- /jobs/[id]

현재 관리하는 것

- 준비 중
- 지원 완료
- 서류 합격
- 면접 예정
- 최종 합격
- 불합격
- 상태 변경 이력
- 마감일
- 면접일
- 팔로업일
- 담당자 연락처
- 체크리스트

이 기능의 의미

북마크는 관심을 저장하는 기능이고,
지원 현황은 실제 지원 과정을 관리하는 기능이다.
JobFilter는 단순히 공고를 찜하는 수준에서 멈추지 않고,
지원 이후의 상태와 후속 행동까지 기록하도록 했다.

3-4. 지원 건 Command Center

지원 건 상세 화면에는 다음 기능으로 이동하는 영역이 있다.

- 자소서 준비
- 면접 연습
- 포트폴리오
- 일정 관리

자소서로 이동할 때 회사명·직무명·jobId를 전달한다.
그래서 특정 지원 건을 기준으로 자소서를 만들 수 있다.

왜 필요한가

실제 학생은 “자소서 페이지”를 사용하는 것이 아니라
“이번 회사에 지원하기 위한 자소서”를 만든다.
이 차이를 반영하려면 기능이 페이지 중심이 아니라 지원 건 중심으로 연결되어야 한다.

현재 정확한 상태

- 화면 이동은 구현되어 있다.
- 자소서와 JobPosting 연결도 구현되어 있다.
- 포트폴리오와 면접은 아직 화면 이동 중심이다.
- 지원 건별 대표 포트폴리오나 면접 답변 수를 자동 집계하는 단계는 아니다.

3-5. 지원 준비율 1차

현재 계산 항목은 네 가지다.

1. 자소서 연결
2. 체크리스트 전체 완료
3. 면접 일정 설정
4. 팔로업 일정 설정

각 항목을 하나의 준비 항목으로 보고 25%씩 계산한다.

이 방식의 장점

- 기존 데이터를 재사용한다.
- 학생에게 이해하기 쉽다.
- 처음부터 복잡한 작업 테이블을 새로 만들지 않아도 된다.

이 방식의 한계

- 포트폴리오와 면접 답변이 아직 직접 반영되지 않는다.
- 체크리스트가 비어 있을 때 완료로 볼지 정책을 더 정해야 한다.
- 실제 제출 완료와 “자료가 존재함”을 더 세밀하게 구분할 필요가 있다.

앞으로의 방향

- 자소서 분석 점수 반영
- 포트폴리오 대표 프로젝트 반영
- 면접 답변 작성 수 반영
- 기술 증거 연결
- 다음 행동 한 가지 자동 추천

3-6. 자소서 룰 기반 코칭

자소서에서 확인하는 항목

- 분량
- 공허한 표현
- 수치 포함 여부
- STAR 구조
- 직군 키워드
- 문장 길이
- 협업 표현
- 첫 문장
- 접속사 반복
- 수동태
- 추상적 표현

왜 AI를 쓰지 않았는가

학생 대상 서비스는 비용이 중요하다.
모든 자소서를 외부 AI API로 보내면 운영비가 계속 발생할 수 있다.
또한 “왜 이런 점수가 나왔는지” 설명하기도 어렵다.

분량·문장 길이·특정 표현·키워드·숫자·STAR 패턴은
정규식과 문자열 분석으로도 충분히 1차 피드백을 줄 수 있다.

다만 이것은 문맥을 완전히 이해하는 AI가 아니다.
따라서 발표에서는 “AI 첨삭”보다 “룰 기반 작성 보조”라고 표현한다.

3-7. 피드백 클릭·문장 하이라이트

동작 순서

분석 실행
→ 경고 피드백 클릭
→ 해당 문항 펼침
→ 문항 위치로 스크롤
→ 문제 표현 하이라이트
→ 사용자가 수정
→ 재분석

이 기능을 추가한 이유

분석 결과가 아무리 좋아도 사용자가 수정 위치를 찾지 못하면 실제 효과가 없다.
그래서 분석 결과와 편집 화면을 직접 연결했다.

3-8. 자소서 버전 diff

- 두 버전 선택
- 변경 문항 수 계산
- 이전 답변은 빨강
- 변경 답변은 초록
- 동일하면 변경 없음 표시
- 이전 버전 복원 가능

점수 그래프는 변화 방향을 보여주고,
diff는 실제 문장 변화를 보여준다.
두 기능을 함께 써야 학생이 자신의 수정 과정을 이해할 수 있다.

3-9. 경험 저장소

저장 구조

- 제목
- 상황
- 행동
- 결과
- 사용 기술
- 수치·성과

사용 예시

“팀 프로젝트 성능 개선”이라는 경험을 저장한다.

상황: 검색 응답이 늦었다.
행동: 쿼리와 캐시 구조를 개선했다.
결과: 응답 시간이 줄었다.
사용 기술: TypeScript, PostgreSQL
성과: 응답 시간 30% 개선

이후 자소서 문항에서 해당 경험을 삽입한다.

왜 필요한가

경험은 자소서 한 번 쓰고 버리는 정보가 아니다.
면접 답변과 포트폴리오 설명에도 사용할 수 있다.
그래서 경험을 독립적으로 저장하면 여러 준비 영역에서 재사용할 수 있다.

3-10. 알림과 대시보드 오늘의 할 일

기존 문제

GET /api/jobs를 호출할 때 알림을 만들고 있었다.
조회만 해도 쓰기가 발생할 수 있고,
목록을 반복해서 열면 중복 확인이 반복될 수 있었다.

수정 방향

- GET /api/jobs는 조회만 한다.
- POST /api/notifications/sync에서 알림을 생성한다.
- 알림 페이지가 동기화 후 목록을 불러온다.

대시보드에 표시하는 작업

- 마감 준비
- 면접 준비
- 팔로업 확인
- 미완료 준비물 확인

주의

별도 `/today` 페이지는 현재 구현하지 않았다.
현재 구현은 대시보드 안의 오늘의 할 일 1차 영역이다.

3-11. 관리자 업로드 dry-run

관리자 업로드 화면의 역할

- Excel·CSV 파일 선택
- 파일 크기·행 수 제한
- 컬럼 매핑
- IT·개발 관련 필터
- 파싱 성공 수
- 중복 예상 수
- 파싱 실패·제외 수
- 직군별 통계
- 선택 등록

왜 필요한가

관리자가 파일을 업로드하자마자 DB에 저장하면
잘못된 데이터가 한 번에 들어갈 수 있다.
그래서 먼저 preview를 보여주고,
관리자가 확인한 행만 등록하게 했다.

현재 한계

- 실패 행 다운로드는 아직 보강 대상이다.
- 실제 등록 중 일부만 실패할 때 행별 결과가 필요하다.
- 대량 등록 원자성 정책이 더 명확해야 한다.

3-12. 리크루터와 공개 구인

현재 구현

- 리크루터 가입
- 관리자 승인
- 승인된 계정만 공고 등록
- 기업 공고 수정·삭제
- 수정 시 재검토를 위해 비활성화
- 입력 schema 검증
- 공개 등록 rate limit

향후 계획

- 학생 공개 동의 필드 세분화
- 리크루터 학생 탐색
- 관심 요청
- 학생 수락·거절
- 민감정보 마스킹

학생 탐색은 기능보다 개인정보 정책이 먼저다.
이메일이나 전화번호를 바로 노출하기보다,
학생이 공개에 동의한 정보만 보여주고 관심 요청을 거치게 해야 한다.

4. 데이터·보안·운영 관점에서의 현재 상태

잘 되어 있는 부분

- JobPosting 상세 조회에 id와 userId 조건을 사용한다.
- Experience API에 userId 조건을 사용한다.
- Recruiter 공고에 recruiterId 소유권을 확인한다.
- Admin API에 ADMIN role 확인이 있다.
- Recruiter API에 role과 isApproved 확인이 있다.
- 공개 구인 API의 입력과 요청 횟수를 제한한다.
- Experience 응답에서 내부 userId를 제외하는 DTO를 적용했다.

아직 보강해야 하는 부분

- 전체 API의 DTO 정리가 끝나지 않았다.
- 실제 Route 세션 통합 테스트가 부족하다.
- Experience migration이 운영 DB에 적용됐는지 확인하지 않았다.
- 알림 중복 키가 body 문자열 검색 기반이다.
- 메모리 rate limiter는 여러 서버 인스턴스에서 전역 제한이 아니다.
- GitHub 외부 요청의 timeout·도메인·응답 크기 제한을 전수 점검해야 한다.

운영 전 필수 확인

1. production DATABASE_URL 확인
2. DIRECT_URL 확인
3. migration status 확인
4. backup 확인
5. prisma migrate deploy
6. 로그인·권한 테스트
7. build 확인
8. 실제 화면 E2E 확인

이유

서비스가 복잡해지고 운영 비용과 개인정보 위험이 커진다.

6. 앞으로 무엇을 하면 좋은가
================================================================================

우선순위 1. API 소유권 통합 테스트

무엇을 하는가
- 다른 사용자의 JobPosting·CoverLetter·Portfolio·Experience·Roadmap 접근 차단을 테스트한다.
- 일반 사용자의 관리자 API 접근을 테스트한다.
- 미승인 리크루터의 변경 API를 테스트한다.

어떻게 하는가
- Vitest에서 세션과 Prisma를 mocking한다.
- 401·403·404 응답 기준을 정한다.
- 각 resource ID를 다른 사용자로 요청하는 테스트를 만든다.

왜 먼저 하는가

기능이 많아져도 다른 사람의 데이터가 보이면 서비스는 사용할 수 없다.
기능 추가보다 우선순위가 높다.

완료 기준

- 권한 오류가 예상 status를 반환한다.
- 타 사용자 데이터가 응답에 포함되지 않는다.
- 삭제·수정 API도 소유권을 확인한다.

우선순위 2. Experience migration 운영 적용 확인

무엇을 하는가
- migration 파일이 실제 DB에 적용됐는지 확인한다.

어떻게 하는가
- 백업
- production 환경변수 확인
- prisma migrate status
- prisma migrate deploy
- 경험 생성·조회·삭제 smoke test

왜 필요한가

로컬에서 Prisma Client가 생성됐다고 운영 DB에 테이블이 생긴 것은 아니다.
Experience API를 배포하기 전에 실제 테이블 적용을 확인해야 한다.

우선순위 3. 전체 API DTO 정리

무엇을 하는가
- Prisma 객체를 그대로 반환하는 route를 줄인다.
- User·JobPosting·Portfolio·JobListing 응답을 명시적으로 만든다.

왜 필요한가

나중에 schema에 필드를 추가했을 때 의도하지 않은 개인정보가 같이 반환될 수 있다.
응답 필드를 명시하면 API 계약과 보안을 관리하기 쉽다.

우선순위 4. 지원 준비 리포트 강화

추가할 것

- 연결된 대표 포트폴리오
- 포트폴리오 프로젝트 수
- 관련 GitHub 분석
- 면접 질문 수
- 작성한 답변 수
- 경험 연결 수
- 공고 요구 기술 중 증거가 없는 기술

구현 방향

현재 CoverLetter·Portfolio·InterviewAnswer는 사용자 단위로 연결되어 있다.
다음에는 JobPosting과 직접 연결하거나,
지원 건별 연결 테이블을 만들어야 한다.

우선순위 5. 로드맵과 공고 기술 연결

흐름

공고 tags
→ 최근 자주 요구되는 기술 집계
→ 사용자 skills 비교
→ RoadmapItem 미완료 확인
→ 학습 추천
→ Portfolio·Experience 증거 연결

결과

“Docker가 부족합니다”에서 끝나는 것이 아니라,
“Docker를 요구하는 공고가 있고, 아직 관련 포트폴리오 증거가 없습니다”까지 보여준다.

우선순위 6. 회사·공고 조사 노트

초기에는 외부 크롤링을 하지 않는다.

지원 건 안에 다음 메모를 저장한다.

- 회사가 하는 일
- 제품·서비스
- 공고 핵심 요구사항
- 지원동기 참고
- 예상 질문
- 면접 전 확인 내용

왜 이렇게 하는가

외부 기업 데이터는 정확성·약관·운영 비용 문제가 있다.
먼저 사용자가 직접 정리하는 메모 기능으로 시작하는 것이 안전하다.

우선순위 7. 지원 활동 분석

개인 화면

- 기간별 지원 수
- 상태별 수
- 서류·면접·최종 전환율
- 자소서 작성률
- 체크리스트 완료율
- 평균 팔로업 기간

관리자 화면

- 개인을 식별할 수 없는 익명 집계
- 표본 수가 적으면 통계 숨김
- 학과·기간 단위 집계

- 로드맵·공고 기술 연결
- 기술 증거 매핑
- 회사·공고 조사 노트
- 지원 활동 분석

- 리크루터 학생 탐색
- 공개 동의 세분화

절대 현재 구현으로 말하면 안 되는 것

9. 최종 발표 문장
================================================================================

“JobFilter는 공고를 많이 보여주는 서비스로 시작했지만,
현재는 학생이 하나의 지원 건을 중심으로 취업 준비를 이어갈 수 있는 서비스로 발전하고 있습니다.

공고에서는 나에게 맞는 이유와 부족한 기술을 보여주고,
지원 건에서는 자소서·체크리스트·일정과 다음 준비 항목을 확인할 수 있습니다.
자소서에서는 룰 기반 피드백을 실제 수정 문장까지 연결하고,
경험 저장소를 통해 학생이 가진 프로젝트 경험을 재사용할 수 있게 했습니다.

현재는 핵심 흐름의 1차 기반이 구현된 상태이고,
앞으로는 포트폴리오·면접 답변의 직접 연결,
API 통합 테스트, 운영 DB migration 확인,
로드맵과 공고 기술 연결을 강화할 예정입니다.

결국 JobFilter의 목표는 기능을 많이 추가하는 것이 아니라,
공고 발견부터 지원 준비와 결과 분석까지의 과정을
학생이 한 곳에서 끊김 없이 관리하도록 만드는 것입니다.”
