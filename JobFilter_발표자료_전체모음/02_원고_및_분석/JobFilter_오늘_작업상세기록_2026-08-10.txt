1. 오늘 작업의 전체 방향
================================================================================

오늘의 우선 방향

1. 발표자료·기능 분석·실행계획을 함께 읽고 현재 구현 상태를 파악했다.
2. 기능 추가보다 보안·입력 검증·데이터 소유권·운영 안정성을 먼저 확인했다.
3. 그 다음 지원 건 중심의 사용자 여정을 보강했다.
4. 완료된 기능과 미완료 기능을 계획서에 표시했다.
5. 실제 소스 변경 뒤 TypeScript·lint·test로 검증했다.
6. 발표자가 “무엇을 왜 만들었는가”를 설명할 수 있도록 별도 보고서를 만들었다.

전체 사용자 흐름

공고 발견
→ 매칭 근거 확인
→ 지원 목록 추가
→ 지원 건 Command Center
→ 준비율 확인
→ 자소서 작성·분석·수정
→ 경험 재사용
→ 면접·포트폴리오 준비
→ 일정·알림 관리
→ 지원 결과 분석

오늘 판단한 핵심
- JobFilter는 기능 수가 부족한 서비스가 아니다.
- 여러 기능이 지원 건 하나를 중심으로 더 단단히 연결되어야 한다.
- 새 기능을 만들 때도 인증·소유권·입력 검증을 함께 넣어야 한다.

3. 매칭 점수 공통 모듈 구현
================================================================================

관련 파일

- app/api/listings/route.ts
- app/api/dashboard/priority-jobs/route.ts

기존 문제

- 공고 목록과 대시보드가 서로 다른 방식으로 점수를 계산할 수 있었다.
- 기술 태그와 직무명 교집합만으로는 근거 설명이 부족했다.
- 숫자 점수만 보여주면 사용자는 부족한 기술을 알 수 없었다.

구현 방법

1. `lib/matching.ts`에 순수 함수 `calculateMatching`을 만들었다.
2. 사용자 skills와 공고 tags를 정규화한다.
3. 문자열 대소문자·공백 차이를 줄인다.
4. 양쪽 문자열 포함 관계를 이용해 기술 일치를 판정한다.
5. matchedSkills와 missingSkills를 만든다.
6. targetJob과 position의 유사도를 계산한다.
7. career 값에서 신입·무관·인턴 조건을 확인한다.
8. deadline으로 긴급도를 계산한다.
9. score와 세부 점수·근거를 반환한다.
10. 목록 API와 priority API가 같은 모듈을 호출하도록 바꾸었다.

반환 데이터

- score
- skillScore
- roleScore
- careerScore
- urgencyScore
- matchedSkills
- missingSkills
- reasons

왜 이렇게 했는가

- 같은 공고가 화면마다 다른 점수로 보이면 신뢰성이 떨어진다.
- 점수보다 “왜 맞는가”와 “무엇이 부족한가”가 학생에게 더 유용하다.
- 순수 함수로 만들면 서버 API와 클라이언트 fallback에서 재사용할 수 있다.
- AI API 없이도 설명 가능한 1차 매칭을 제공할 수 있다.

테스트

- React 기술 일치 확인
- Docker·AWS 부족 기술 확인
- 목표 직무 유사 근거 확인
- 프로필 정보가 없을 때 오류 없이 처리
- 잘못된 JSON 배열 처리

관련 파일

구현 내용

지원 상세 화면에 다음 이동 영역을 넣었다.

자소서 이동 시 다음 정보를 전달한다.

- position
- jobId

이를 통해 자소서가 특정 지원 건과 연결된다.

지원 준비 리포트 1차

지원 건 상세에서 다음을 계산한다.

- 자소서 연결 여부
- 체크리스트 전체 완료 여부
- 면접 일정 설정 여부
- 팔로업 일정 설정 여부
- 최근 자소서 분석 점수

준비율은 4개 항목 중 완료된 수를 비율로 변환한다.

왜 이렇게 했는가

- 지원 건을 기능 연결의 중심으로 만들기 위해서다.
- 학생이 여러 메뉴를 돌아다니지 않고 준비 상태를 볼 수 있어야 한다.
- 기존 JobPosting·CoverLetter·checklist 데이터를 재사용해 DB 구조를 불필요하게 늘리지 않았다.

API 변경

- `/api/jobs/[id]` 조회에 연결된 자소서 최소 정보만 포함했다.
- 자소서 원문 전체를 지원 상세 API에 넣지 않았다.
- 자소서 id·version·analysisScore·updatedAt만 반환한다.
- JobPosting 조회에는 userId 조건이 있어 타 사용자 접근을 차단한다.

현재 한계

- 포트폴리오와 InterviewAnswer를 지원 건별로 직접 연결하는 모델은 아직 없다.
- 준비 리포트는 1차 상태 요약이며, 실제 면접 답변 수와 대표 프로젝트까지는 다음 단계다.

5. 자소서 분석 피드백 이동·하이라이트
================================================================================

관련 파일

- app/(dashboard)/cover-letter/page.tsx
- lib/cover-letter-analysis.ts
- app/api/cover-letter/analyze/route.ts

기존 문제

- 분석 결과를 확인한 뒤 어느 문장으로 이동해야 하는지 사용자가 직접 찾아야 했다.
- 히트맵은 일부 키워드에 연결되었지만 일반 분석 피드백과 편집 위치 연결이 약했다.

구현 방법

1. 피드백 메시지에서 따옴표 안의 표현을 추출한다.
2. 첫 문장·수동태·접속사·추상 표현은 후보 표현 목록을 사용한다.
3. 자소서 문항을 순회하며 해당 표현이 포함된 문항을 찾는다.
4. 클릭 시 부모 페이지에 focus 정보를 전달한다.
5. 해당 자소서 카드를 자동으로 펼친다.
6. 해당 문항 DOM으로 스크롤한다.
7. `HighlightedAnswer`가 해당 키워드를 mark 태그로 강조한다.

지원 예시

- “최선을 다하겠습니다”
- “저는”으로 시작하는 문장
- “그리고”, “또한”, “하지만” 반복
- “되었습니다”, “받았습니다” 같은 수동 표현
- “다양한”, “여러”, “많은” 같은 추상 표현

왜 이렇게 했는가

- 분석 결과가 실제 수정 행동으로 이어져야 하기 때문이다.
- 룰 기반 분석의 장점인 정확한 문자열 위치를 UI와 연결할 수 있다.
- 외부 AI API 없이도 작성 흐름을 개선할 수 있다.

안내 원칙

- 룰 기반 결과는 합격 판정이 아니다.
- 문맥을 완전히 이해하지 못할 수 있다.
- 작성 보조 피드백으로 안내한다.

- 수정 전·후를 직접 보여주면 사용자가 어떤 개선을 했는지 확인할 수 있다.

7. 경험 저장소 구현
================================================================================

관련 파일

- prisma/schema.prisma
- prisma/migrations/20260810000000_add_experience/migration.sql
- app/api/experiences/route.ts
- app/api/experiences/[id]/route.ts
- components/cover-letter/ExperienceLibrary.tsx

데이터 구조

- title: 경험 제목
- situation: 상황
- action: 행동
- result: 결과
- technologies: 사용 기술 JSON 배열
- metrics: 수치·성과
- userId: 소유 사용자
- createdAt·updatedAt

API

- GET /api/experiences
- POST /api/experiences
- PATCH /api/experiences/:id
- DELETE /api/experiences/:id

구현 방법

- 조회는 userId로 본인 경험만 가져온다.
- 생성 시 제목·상황·행동·결과를 필수로 받는다.
- 제목은 100자, 주요 내용은 2,000자 이내로 제한한다.
- technologies는 배열을 JSON 문자열로 저장하고 응답 시 배열로 복원한다.
- 수정·삭제 전 id와 userId로 소유권을 확인한다.
- API 응답은 내부 userId를 제외한 DTO로 만든다.

화면 동작

- 자소서 작성 SlideOver 안에 경험 저장소를 표시한다.
- 새 경험을 등록한다.
- 기존 경험을 삭제한다.
- 경험을 첫 번째 자소서 문항에 STAR 형식으로 삽입한다.

왜 이렇게 했는가

- 같은 프로젝트 경험을 반복해서 입력하지 않도록 하기 위해서다.
- STAR 구조는 자소서와 면접에서 동시에 재사용할 수 있다.
- 학생이 직접 입력한 경험 데이터를 중심으로 운영해 AI 비용을 줄인다.

DB 주의

- schema.prisma에 Experience 모델을 추가했다.
- migration.sql을 추가했다.
- `npx prisma generate`를 실행해 generated Client를 갱신했다.
- 운영 DB 적용은 별도로 `prisma migrate deploy` 확인이 필요하다.
- migration 적용 전 DATABASE_URL·DIRECT_URL이 올바른 환경을 가리키는지 확인해야 한다.

기존 문제

- GET /api/jobs 조회에 알림 생성 부작용이 있었다.
- 반복 조회 때마다 중복 검사가 발생할 수 있었다.

구현 내용

- GET /api/jobs는 지원 공고 조회만 수행한다.
- POST /api/notifications/sync를 새로 분리했다.
- 마감 임박·면접·팔로업 알림을 sync에서 생성한다.
- 알림 목록 화면은 sync 후 GET 목록을 호출한다.
- 대시보드에는 마감·면접·팔로업·미완료 체크리스트를 표시한다.
- 긴급과 준비 작업을 구분한다.
- 각 항목에서 지원 건 상세로 이동한다.

왜 이렇게 했는가

- GET은 읽기 동작으로 유지하는 것이 예측 가능하다.
- 알림 생성 시점을 분리하면 DB 쓰기와 중복을 통제하기 쉽다.
- 대시보드에서 학생이 지금 해야 할 일을 바로 확인할 수 있다.

정정 사항

- 별도의 `/today` 페이지를 만들라는 요청이 아니었는데 한때 잘못 해석해 생성했다.
- 다음 파일을 생성했다가 사용자 요청에 따라 제거했다.
  - app/(dashboard)/today/page.tsx
  - lib/today-tasks.ts
  - lib/today-tasks.test.ts
- 대시보드의 `/today` 링크도 제거했다.
- 현재 실제 구현으로 남아 있는 것은 대시보드 안의 오늘의 할 일 1차 영역이다.
- 별도 오늘 페이지는 현재 미구현이다.

- 미리보기 단계에서는 DB에 저장하지 않음
- dry-run임을 화면에 표시

왜 이렇게 했는가

- 학교 Excel은 공고 형식과 품질이 일정하지 않을 수 있다.
- 잘못된 날짜·중복·무관 직무가 DB에 들어가는 것을 방지한다.
- 관리자가 결과를 확인한 뒤 선택적으로 등록하게 한다.

남은 개선

- 실패 행 다운로드
- 날짜·인코딩 오류 상세 표시
- 실제 등록 결과와 미리보기 차이 표시
- 행별 처리 결과와 감사 로그
- transaction 또는 부분 실패 처리

10. 리크루터·공개 구인 API 입력 검증과 rate limit
================================================================================

관련 파일

- lib/validations/recruiter.ts
- app/api/recruiter/listings/route.ts
- app/api/recruiter/listings/[id]/route.ts
- app/api/recruit/route.ts
- app/api/auth/register-recruiter/route.ts
- lib/security.ts

검증 내용

- 회사명·직무 필수
- 회사명·직무 길이 제한
- 설명·지역·급여 길이 제한
- URL http/https만 허용
- 날짜 유효성
- 태그 개수·길이 제한
- 담당자 이메일 형식
- 가입 비밀번호 8자·영문·숫자 조건
- 공개 업로드 5MB·50행 제한

권한 내용

- 리크루터 role 확인
- 리크루터 isApproved 확인
- 자신의 recruiterId 공고만 수정·삭제
- 관리자가 검토하기 전 isActive=false

rate limit

- 공개 구인 등록 요청 제한
- 리크루터 가입 요청 제한
- IP 헤더를 기준 식별자로 사용
- 제한 초과 시 429 반환

왜 이렇게 했는가

- 공개 API는 로그인 없이 호출 가능하므로 악성 반복 요청 위험이 있다.
- DB에 잘못된 문자열·URL·날짜가 저장되는 것을 막아야 한다.
- 기업 공고는 학생에게 노출되기 전 관리자 검토가 필요하다.

현재 한계

- SimpleRateLimiter는 메모리 기반이다.
- Vercel 여러 인스턴스에서는 전역 rate limit이 아니다.
- 운영 규모가 커지면 Redis·Upstash 기반으로 바꿔야 한다.

11. API 응답·보안·소유권 점검
================================================================================

경험 API DTO

- 내부 userId를 직접 반환하지 않도록 명시적 DTO를 사용했다.
- technologies는 저장 형식과 API 표시 형식을 분리했다.

지원 상세 API

- id와 userId를 함께 조건에 넣어 지원 건 소유권을 확인한다.
- 연결된 자소서는 최소 필드만 반환한다.

공통 소유권 테스트

- validateUserAccess 함수 테스트를 추가했다.
- 동일 userId는 true를 반환한다.
- 다른 userId는 false를 반환한다.

아직 필요한 보안 테스트

- 실제 API Route 세션 mocking
- 타 사용자 JobPosting ID 접근
- 타 사용자 CoverLetter ID 접근
- 타 사용자 Portfolio·Experience·Roadmap ID 접근
- 미승인 recruiter의 모든 변경 API
- USER의 admin API 접근

12. 테스트·검증 결과
================================================================================

실행한 검증 명령

1. npx prisma generate
- Experience 모델을 포함한 Prisma Client 생성

2. npx tsc --noEmit
- TypeScript 타입 오류 없음

3. npm run lint
- ESLint 경고·오류 없음

4. npm run test -- --reporter=dot
- 테스트 3개 파일 통과
- 총 6개 테스트 통과

실행하지 않은 검증

- 운영 DB에 migration 적용
- 실제 Vercel production build·배포
- 실제 브라우저 E2E
- 다중 인스턴스 rate limit

실행하지 않은 이유

- 운영 DB 연결과 배포는 실제 환경에 영향을 줄 수 있다.
- 현재 작업 트리에 사용자 수정사항이 많아 먼저 기준선과 승인 절차가 필요하다.
- 운영 DB migration은 DATABASE_URL·DIRECT_URL 확인 후 별도로 실행해야 한다.

14. 발표용 결론
================================================================================

오늘 작업의 결론

JobFilter는 기능을 무작정 추가한 것이 아니라,
공고와 지원 준비가 연결되도록 핵심 흐름을 강화했다.

가장 큰 변화

- 점수만 보여주던 매칭을 근거 중심으로 바꾸었다.
- 지원 건 상세에서 준비 기능으로 이동할 수 있게 했다.
- 자소서 분석 결과를 실제 문장 수정으로 연결했다.
- 경험 저장소로 STAR 경험을 재사용하게 했다.
- 버전 간 수정 내용을 비교하게 했다.
- GET 요청의 알림 생성 부작용을 제거했다.
- 관리자·리크루터·공개 구인 API의 입력과 요청을 제한했다.
- 계획서와 테스트로 구현 상태를 기록했다.

발표 마무리 문장

“JobFilter의 핵심은 페이지 수가 아니라 연결성입니다.
학생이 공고를 발견한 순간부터 지원 준비, 자소서 개선, 면접 준비,
일정 관리와 결과 분석까지 하나의 지원 건으로 이어지도록 만들었습니다.
오늘의 구현은 그 연결을 안정적으로 운영하기 위한 기반을 마련한 작업입니다.”
