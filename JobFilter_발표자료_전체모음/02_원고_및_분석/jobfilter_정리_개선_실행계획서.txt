0. 분석 결론 요약
================================================================================

JobFilter는 Next.js 14 App Router + Prisma/PostgreSQL + NextAuth Credentials 기반의
취업 공고, 지원 현황, 자소서 코칭, 면접, 로드맵, 포트폴리오 통합 서비스다.
기능 범위는 상당히 넓고 핵심 사용자 흐름도 구현되어 있으나, 현재 저장소는 다음
네 가지 위험이 함께 존재한다.

1) 작업 트리가 매우 지저분하다.
   - 30개가 넘는 추적 파일이 수정 상태이고, 신규 기능 파일도 다수 미추적이다.
   - 특히 lib/generated/prisma가 직접 수정/추적된 상태이며 tmp query-engine 파일도 있다.
   - 따라서 정리 전에 현재 변경사항을 기능별 커밋 또는 별도 백업으로 보존해야 한다.

2) 문서·발표 산출물과 제품 소스가 한 디렉터리에 섞여 있다.
   - jobfilter_분석.txt, jobfilter_발표.html은 유용하지만 운영 코드와 분리하는 편이 좋다.
   - reports/에는 과거 기능 추천·작업 보고서가 있어 문서 산출물과 운영 코드를 분리할 필요가 있다.

3) 테스트 기반이 사실상 없다.
   - package.json에는 Vitest가 있으나 test 파일이 발견되지 않았다.
   - npm run lint는 성공했지만 npm test는 “No test files found”로 종료 코드 1이다.

4) 보안·운영 보강이 필요하다.
   - 메모리 기반 rate limiter는 Vercel 다중 인스턴스 환경에서 전역 제한이 아니다.
   - lib/security.ts에 정의된 보안 유틸 상당수가 실제 사용되지 않는다.
   - middleware 보호 경로와 API별 인증/인가를 별도로 전수 점검해야 한다.
   - API 응답에서 User 전체 객체를 반환하는 경로가 없는지 확인해야 한다.

가장 중요한 원칙:
- 지금은 무작정 삭제하지 않는다.
- Git 변경사항을 먼저 분리·검증한다.
- generated Prisma 파일은 schema와 generate 전략을 정리한 뒤 삭제/비추적한다.
- 기능 삭제는 사용처 검색, 라우트 접근성 확인, 배포 동작 확인 후에만 한다.

================================================================================
6. 보안 분석 및 우선 개선 항목
================================================================================

P0 - 즉시 확인

1. 인증/인가 전수 점검
- middleware는 /dashboard, /portfolio, /jobs, /roadmap, /interview,
  /profile, /calendar, /admin만 보호한다.
- /bookmarks, /listings, /notices, /notifications, /cover-letter,
  /recruiter 등은 페이지/서버/API 자체에서 인증하는지 각각 확인한다.
- middleware는 보조 장치일 뿐이고 API route마다 session + userId 소유권 검사가
  반드시 있어야 한다.

2. 관리자·리크루터 권한 검사
- ADMIN API는 role을 검사하고, RECRUITER API는 role과 isApproved를 모두 검사한다.
- 특히 recruiter listings/[id]의 수정/삭제에서 해당 listing의 recruiterId가
  현재 사용자와 일치하는지 확인한다.
- user role을 클라이언트 입력값으로 신뢰하지 않는다.

3. 비밀번호 재설정
- forgot-password 응답에서 이메일 존재 여부가 노출되어 계정 열거가 가능한지 확인한다.
- reset token은 평문 DB 저장보다 해시 저장, 만료/1회 사용/재사용 방지,
  요청 rate limit을 적용한다.
- 메일 발송이 실제 구현되지 않았다면 운영 기능으로 표시하지 않는다.

4. 메모리 rate limiter
- lib/security.ts의 SimpleRateLimiter는 서버 인스턴스 메모리만 사용한다.
- Vercel serverless 환경에서는 인스턴스 간 공유되지 않으므로 인증/비밀번호
  재설정 보호 수단으로 충분하지 않다.
- 외부 Redis/Upstash 등 영속 저장소 도입 또는 플랫폼 WAF/방화벽 정책을 검토한다.

5. Origin 검증 버그 가능성
- validateOrigin은 originUrl.hostname과 host를 직접 비교한다.
- host에는 포트가 포함될 수 있어 localhost:3000에서 false가 될 수 있다.
- URL의 hostname/port를 분리해 비교하고 신뢰된 origin allowlist를 사용한다.

P1 - 다음 단계

6. 보안 헤더 실제 적용
- getSecurityHeaders가 정의되어 있어도 모든 응답에 자동 적용되지 않으면 효과가 없다.
- next.config.js headers 또는 middleware에서 CSP, HSTS(HTTPS 운영 시),
  frame-ancestors 등을 환경에 맞게 적용한다.
- X-XSS-Protection은 현대 브라우저에서 실효성이 낮으므로 CSP 중심으로 설계한다.

7. 입력 크기와 파일 업로드 제한
- xlsx 업로드의 파일 크기, 행 수, MIME/확장자, 파싱 실패, 악성 수식/셀 내용,
  타임아웃을 제한한다.
- 문자열 필드의 최대 길이와 JSON string 컬럼의 스키마를 zod로 검증한다.

8. 민감정보 최소 반환
- User 전체 객체를 API 응답으로 반환하지 말고 select로 필요한 필드만 선택한다.
- password, reset token, email, recruiter 비공개 필드는 응답/로그에서 제외한다.
- recruiter 공개 프로필은 visibility-config를 실제 API 응답 생성에도 적용한다.

9. 외부 URL 검증
- GitHub URL 검증은 현재 단순 정규식이다. URL parsing, github.com hostname,
  사용자명/저장소명 규칙, redirect/SSRF 방지, 요청 timeout을 적용한다.
- fetch 대상은 github.com으로 제한하고 사용자 입력 URL을 임의 서버로 전달하지 않는다.

================================================================================
7. 데이터 모델 및 Prisma 분석
================================================================================

현재 모델군:
User, Portfolio, JobPosting, StatusHistory, RoadmapItem, InterviewQuestion,
InterviewAnswer, CoverLetter, CoverLetterVersion, JobListing, JobBookmark,
EmploymentRecord, Notice, UserNotification, PasswordResetToken 등.

개선 권고:

1. String JSON 컬럼의 타입 안전성
- skills, techStack, contacts, checklist, referenceLinks, items, tags,
  analysisHistory, githubAnalysis가 String JSON으로 저장된다.
- 저장/조회 시 zod schema를 공통화하고 parse 실패를 안전하게 처리한다.
- 장기적으로 PostgreSQL jsonb 또는 별도 relation을 검토한다.

2. enum 도입
- role, JobPosting.status, RoadmapItem.status, category 등은 현재 String이다.
- 잘못된 상태값 유입을 막기 위해 Prisma enum 또는 애플리케이션 enum + zod를 사용한다.
- migration 영향이 있으므로 별도 데이터 마이그레이션으로 진행한다.

3. 인덱스 점검
- userId, deadline, isActive, recruiterId, createdAt, status 등에 실제 조회 패턴에
  맞는 인덱스를 검토한다.
- JobBookmark는 userId/listingId unique가 이미 있다.
- 운영 데이터 규모를 기준으로 EXPLAIN과 쿼리 시간을 측정한다.

4. CoverLetterVersion 정합성
- version 중복 방지를 위한 (coverLetterId, version) unique 제약을 검토한다.
- “최대 10개” 정리 로직을 transaction으로 묶어 동시 저장 시 경쟁 조건을 막는다.

5. generated Prisma 관리
- `prisma generate`가 build/postinstall에서 실행되므로 생성물의 Git 추적 여부를
  팀 정책으로 결정한다.
- 현재 소스가 lib/generated/prisma를 직접 import하므로 먼저 import 경로와 generator
  output을 정리해야 한다. 단순 삭제 금지.

11. 웹 조사 근거 및 적용 포인트

조사한 공식/권위 자료:

1) Next.js Production Checklist
https://nextjs.org/docs/app/guides/production-checklist
- 환경변수 비밀값 관리, NEXT_PUBLIC 노출 범위, CSP/보안 헤더,
  성능·모니터링·검증을 production checklist로 확인할 수 있다.
- 본 계획의 env, CSP, 운영 검증 항목에 반영했다.

https://www.prisma.io/docs/orm/prisma-client/setup-and-configuration/generating-prisma-client
- generator output과 `prisma generate`의 관계를 기준으로 generated client를
  임의 편집/삭제하지 않고 생성 정책부터 정리하도록 했다.

https://next-auth.js.org/providers/credentials
- Credentials Provider는 비밀번호 기반 인증의 보안 책임이 애플리케이션에
  크게 남는 방식이다. 따라서 rate limit, reset token, session/role 검증을
  별도로 강화해야 한다.

4) Next.js Vitest Guide
https://nextjs.org/docs/14/app/building-your-application/testing/vitest
- Vitest + React Testing Library 조합을 기준으로 단위/UI 테스트 계획을 세웠다.
