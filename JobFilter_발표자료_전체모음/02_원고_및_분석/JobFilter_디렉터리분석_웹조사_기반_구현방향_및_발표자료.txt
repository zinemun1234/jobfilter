================================================================================

문서 위치: JobFilter_발표자료_전체모음
조사 범위: 실제 소스코드, Prisma schema, API Route, 페이지 + 외부 유사 서비스(Jobotrak, JobHunt, ApplyArc, ApplyWave, Jobscan, Prentus, FresherBot, Notion 템플릿 등)

이 문서의 목적
- 실제 디렉터리와 웹 조사를 바탕으로 JobFilter가 지금 어디까지 왔는지, 어디를 보완해야 하는지 정리한다.
- 발표 원고처럼 읽을 수 있도록 "문제 → 구현 → 동작 → 사용자 가치 → 현재 한계 → 다음 단계" 순서로 구성한다.
- Today’s Tasks는 별도 개발 범위에서 제외한다.
- 외부 서비스의 좋은 아이디어를 그대로 복제하지 않고, JobFilter의 AI-프리·rule-based·증거 중심 방향에 맞게 재해석한다.

발표 기준
- "현재 구현"은 실제 소스·API·Prisma schema·migration에서 확인된 기능이다.
- "1차 구현"은 핵심 흐름은 동작하지만 데이터 직접 연결이나 운영 검증이 남은 기능이다.
- "보완 필요"는 기능은 있으나 보안·성능·정합성·DTO·운영 적용 등 추가 검증이 필요한 기능이다.
- "향후 계획"은 화면 이동·기획·부분 기반만 있고 완전한 기능으로 말하면 안 되는 항목이다.
- "제외"는 Today’s Tasks처럼 현재 개발/발표 범위에서 뺀 항목이다.

주의할 말투
- 화면에 버튼이 있는 것과 실제 데이터가 완전히 연결된 것은 다르다.
- migration 파일이 있는 것과 운영 DB에 적용된 것은 다르다.
- 단위 테스트 통과와 실제 사용자 E2E 검증은 다르다.
- AI API를 사용하지 않는다. 핵심 기능은 키워드 매칭·정규표현식·룰 기반으로 구현했다.

1. 외부 서비스에서 본 핵심 흐름
================================================================================

Jobotrak, JobHunt, ApplyArc, ApplyWave, Notion Job Tracker 등 대부분의 취업 준비 도구는 다음 흐름을 기본으로 한다.

공고/역할 저장
  → 한 장의 "지원 건 카드"에 모든 맥락 모음
     (회사, JD, 연락처, 이력서 버전, 자소서, 면접 노트, 팔로업)
  → Kanban/보드로 상태 이동
  → 마감·면접·팔로업 알림
  → 상태별 전환율·체류 시간 분석
  → 다음 행동(next action) 추천

즉, 외부 서비스의 경쟁력은 "단순히 공고를 보여주는 것"이 아니라 "지원 건 하나에 모든 준비 맥락을 붙이는 것"이다.

JobFilter도 이미 이 방향으로 가고 있다. 다만 아직 데이터 직접 연결이 부족해서 "화면 이동" 수준에 머물러 있다.

3. 외부 서비스와의 비교
================================================================================

--------------------------------------------------------------------------------
3-1. 지원 건 통합 카드
--------------------------------------------------------------------------------

외부 사례: JobHunt, ApplyArc, ApplyWave, Notion Job Tracker
핵심: "Every application becomes its own workspace." 지원 건 한 장에 JD, notes, contacts, documents, interview roadmap, follow-up을 모두 연결.

JobFilter 상태: Command Center에 이동 버튼은 있지만, 포트폴리오와 면접 답변은 지원 건에 직접 연결되지 않음.

적용 방향: Portfolio, InterviewAnswer에 jobId를 추가하고, /jobs/[id]에서 연결된 자료를 직접 보여준다.

--------------------------------------------------------------------------------
3-2. 지원 건별 이력서/자소서 버전 연결
--------------------------------------------------------------------------------

외부 사례: Swooped, ApplyArc, JobHunt
핵심: "Track which resume you sent to each company." 지원 건마다 사용한 이력서/자소서 버전과 면접 노트를 저장.

JobFilter 상태: 자소서 버전 관리와 지원 건 연결은 있음. 포트폴리오 버전/지원 건 연결은 없음.

적용 방향: 포트폴리오를 지원 건에 연결하고, 어떤 경험/자소서/포트폴리오를 제출했는지 기록.

--------------------------------------------------------------------------------
3-3. ATS/자소서 호환성 체크
--------------------------------------------------------------------------------

외부 사례: Jobscan
핵심: 이력서와 JD 키워드 매칭, ATS parsing 친화적 형식 체크(표/헤더/푸터 금지, 키워드 자연스러운 포함, 키워드 과다 채우기 경고, 표준 섹션 제목).

JobFilter 상태: 자소서 내용 분석(키워드, STAR, 문장 길이)은 있지만, ATS 형식 체크는 없음.

적용 방향: rule-based ATS 형식 체크리스트를 자소서 분석에 추가.

--------------------------------------------------------------------------------
3-4. 면접 회고
--------------------------------------------------------------------------------

외부 사례: TalkHiring, Prentus AI Interview, EzIntervuez
핵심: 면접 후 피드백, 자신감, 예상 밖 질문, 개선점을 회차별로 기록.

JobFilter 상태: 면접 질문·답변 저장까지만 있음.

적용 방향: InterviewAnswer에 회차, 자신감, unexpectedQuestions, improvements, interviewedAt 필드를 추가.

--------------------------------------------------------------------------------
3-5. 기술 증거 매핑
--------------------------------------------------------------------------------

외부 사례: CareerFit, JobFit Agent, CareerProof
핵심: JD 요구사항 → 후보자 증거(포트폴리오, 경험, GitHub, 로드맵) 매핑. direct evidence, transferable evidence, proof gap, gap-mitigation action.

JobFilter 상태: 매칭 점수는 있지만, "이 요구사항을 어떤 증거로 충족하는가"는 없음.

적용 방향: 공고 tags와 사용자 skills, Portfolio.techStack, Experience.technologies, RoadmapItem.status, CoverLetter.items를 비교해 requirement-to-proof map 생성.

--------------------------------------------------------------------------------
3-6. 지원 활동 분석
--------------------------------------------------------------------------------

외부 사례: ApplyWave, Blacknave
핵심: time in stage, response rate, offer rate, conversion funnel.

JobFilter 상태: StatusHistory 데이터가 있지만 집계·시각화는 없음.

적용 방향: StatusHistory 기반으로 상태별 전환율, 평균 체류 시간, 응답률 계산.

--------------------------------------------------------------------------------
3-7. 리크루터-학생 연결 프라이버시
--------------------------------------------------------------------------------

외부 사례: FresherBot, Prentus Talent Links, SourceHire
핵심: 학생 동의 기반 공개, PII 마스킹, scoped access, audit log, direct contact 차단.

JobFilter 상태: 리크루터 공고 등록까지만 구현.

적용 방향: 학생별 공개 동의 필드, 이메일/전화 기본 비공개, 관심 요청 → 학생 수락 → 연락처 공개 흐름 설계.

[분류: 보완 필요] 지원 건과 포트폴리오·면접 답변 직접 연결
--------------------------------------------------------------------------------

문제: 포트폴리오와 면접 답변이 사용자 전역 데이터라서, A 회사 지원용과 B 회사 지원용을 구분할 수 없다.

구현:
1. Prisma schema 변경
   - Portfolio에 jobId String? 추가
   - InterviewAnswer에 jobId String? 추가
2. API 변경
   - POST /api/portfolio에 jobId optional
   - POST /api/interview/answers에 jobId optional
   - GET /api/jobs/[id]에서 portfolios, interviewAnswers include
3. UI 변경
   - /jobs/[id]에서 연결된 포트폴리오/면접 답변 목록 표시
   - /portfolio, /interview에서 지원 건 선택 드롭다운 추가

동작: 학생이 /jobs/[id]에 들어가면 해당 회사에 연결된 포트폴리오와 면접 답변을 본다.

사용자 가치: Command Center가 단순 링크 모음에서 진짜 통합 준비 워크스페이스로 바뀐다.

현재 한계: schema에 아직 jobId가 없어 migration 필요.

다음 단계: 연결 후 준비율과 기술 증거 매핑에 반영.

발표 말투: "포트폴리오와 면접 답변을 지원 건에 직접 연결하는 1차 구조를 구현했습니다."

--------------------------------------------------------------------------------

[분류: 보완 필요] 지원 준비율을 실제 데이터 기반으로 개선
--------------------------------------------------------------------------------

문제: 현재 4개 항목을 25%씩 단순 boolean으로 계산해서 실제 제출 가능성과 다르게 보일 수 있다.

구현:
- lib/readiness.ts에 공통 함수 추가
- 가중치 예시:
  - 자소서 연결 + 분석 점수: 30%
  - 체크리스트 완료율: 20%
  - 포트폴리오 연결: 20%
  - 면접 답변 작성: 15%
  - 일정 설정: 15%
- /api/jobs/[id]에서 readinessScore 계산 후 응답
- /jobs/[id] UI에서 readinessItems 동적 생성
- /jobs 목록과 /dashboard에 준비율 badge

동작: 지원 건의 실제 준비 상태를 0~100%로 보여준다.

사용자 가치: "이 지원 건이 실제로 제출 가능한가"를 한눈에 본다.

현재 한계: 포트폴리오·면접 답변이 연결되지 않으면 가중치를 부여할 수 없다.

다음 단계: 1번 연결 작업 후 즉시 적용.

발표 말투: "지원 준비율은 현재 1차 지표입니다. 향후 실제 자료 연결을 반영해 개선할 계획입니다."

--------------------------------------------------------------------------------

[분류: 보완 필요] API 보안·권한 정리
--------------------------------------------------------------------------------

문제: 일부 API에서 승인 여부 재검증이 빠지거나, Prisma 객체를 spread해서 민감정보가 포함될 수 있다.

구현:
- /api/recruiter/listings/[id] PUT/DELETE에서 isApproved 재확인
- /api/jobs/[id] PATCH에서 userId 조건 검토
- 전체 API DTO 변환 함수 도입
  - User: password, email, companyDesc 제외
  - JobPosting: userId 제외
  - Portfolio, InterviewAnswer 등 userId 제외
- lib/api.ts 공통 응답/에러 처리 적용 확대

동작: 모든 API에서 세션 → 리소스 소유권 → role 확인 → DTO 반환 순서로 동작.

사용자 가치: 다른 사용자의 데이터 노출·악용 위험을 줄인다.

현재 한계: 통합 권한 테스트는 아직 없다.

다음 단계: Vitest로 API 통합 권한 테스트 작성.

발표 말투: "API 보안은 서버에서 세션과 role을 직접 검증하며, DTO 변환으로 민감정보를 제외합니다."

P1. 발표에서 차별화되는 기능
--------------------------------------------------------------------------------

[분류: 향후 계획] 회사·공고 조사 노트
--------------------------------------------------------------------------------

문제: 지원한 회사에 대한 조사 메모, 지원 동기, 예상 질문, JD 핵심 키워드를 따로 기록할 공간이 없다.

구현:
- JobPosting에 research String? JSON 추가
  - motivation, companyNotes, jdKeywords, expectedQuestions, links
- /jobs/[id]/research 탭 또는 /jobs/[id] 하위 섹션
- JD 키워드를 /cover-letter 화면에서도 노출

동작: 학생이 회사 조사와 자소서·면접 준비를 같은 지원 건 안에서 연결한다.

사용자 가치: "왜 이 회사인가"를 지원 건 단위로 기록하고, 자소서/면접에서 꺼내 쓸 수 있다.

현재 한계: schema 미구현.

다음 단계: 자소서 작성 시 JD 키워드 자동 표시 연결.

발표 말투: "회사·공고 조사 노트는 향후 지원 건별 메모로 추가할 계획입니다."

--------------------------------------------------------------------------------

[분류: 향후 계획] 면접 회고
--------------------------------------------------------------------------------

문제: 면접을 봤지만 회차별로 무엇을 배웠는지, 다음에 어떻게 개선할지 기록하지 못한다.

구현:
- InterviewAnswer에 round, confidence, unexpectedQuestions, interviewerFeedback, improvements, interviewedAt 추가
- /interview 화면에 회고 탭
- /jobs/[id]에서 회차별 회고 목록

동작: 면접 본 뒤 답변, 자신감, 피드백, 개선점을 같은 질문과 연결해 기록.

사용자 가치: 면접 후 학습 루프가 형성된다.

현재 한계: InterviewAnswer는 질문-답변 저장만 가능.

다음 단계: 회차별 통계 및 다음 면접 권장 액션.

발표 말투: "면접 회고는 질문-답변 저장을 넘어 회차별 성찰로 확장할 계획입니다."

--------------------------------------------------------------------------------

[분류: 향후 계획] 기술 증거 매핑
--------------------------------------------------------------------------------

문제: 공고가 "Docker"를 요구하면, 사용자가 어떤 포트폴리오/경험/로드맵으로 이를 증명하는지 보이지 않는다.

구현:
- 공고 tags × 사용자 skills 비교
- 각 tag에 대해 다음 증거 검색:
  - Portfolio.techStack 포함
  - Experience.technologies 포함
  - RoadmapItem.status === COMPLETED
  - CoverLetter.items 내용에 포함
- 결과를 "증거 있음 / 부족 / 학습 필요"로 분류
- /listings/[id] 또는 /jobs/[id]에 표시

동작: 공고 요구 기술마다 사용자가 갖는 증거와 부족한 점을 맵 형태로 보여준다.

사용자 가치: "이 기술을 가졌다"에서 "이 기술을 증명할 수 있다"로 이동한다.

현재 한계: 데이터 직접 연결이 필요.

다음 단계: 로드맵 항목과 공고 기술 연결.

발표 말투: "매칭 점수는 참고 지표이며, 향후 '기술 요구 ↔ 내 증거' 매핑으로 발전할 계획입니다."

--------------------------------------------------------------------------------

[분류: 향후 계획] ATS/자소서 형식 체크리스트
--------------------------------------------------------------------------------

문제: 자소서 내용은 분석하지만, ATS parsing에 적합한 형식인지는 체크하지 않는다.

구현:
- lib/cover-letter-analysis.ts에 rule-based ATS 체크 추가
  - 표/칼럼/헤더/푸터 사용 감지
  - 표준 섹션 제목 여부
  - 키워드 과다 채우기(stuffing) 경고
  - 약어와 풀네임 모두 포함 권장
  - PDF 파일 형식 권장
- /cover-letter 분석 결과에 "ATS 호환성" 패널 추가

동작: 자소서 작성 시 형식 문제도 함께 피드백.

사용자 가치: 내용뿐 아니라 형식도 ATS를 통과할 수 있게 준비.

현재 한계: 미구현.

다음 단계: JD 키워드와 연동한 자소서 맞춤도 피드백.

발표 말투: "ATS 형식 체크리스트는 rule 기반으로 추가할 예정이며, AI 없이 운영 가능합니다."

--------------------------------------------------------------------------------

[분류: 향후 계획] 지원 활동 분석
--------------------------------------------------------------------------------

문제: StatusHistory 데이터가 있지만, 상태별 전환율이나 평균 체류 시간을 보여주지 않는다.

구현:
- lib/analytics.ts 추가
  - 기간별 지원 수
  - 상태별 전환율
  - 평균 상태 체류 시간
  - 응답률
- /dashboard 또는 /jobs 상단에 통계 카드
- /admin/stats에서 학급/학과 단위 익명 집계

동작: 학생이 "내 지원이 어디에서 막히는가"를 본다.

사용자 가치: 지원 전략을 데이터로 개선.

현재 한계: StatusHistory 데이터만 존재, 집계 로직 없음.

다음 단계: 관리자 개입 포인트 분석.

발표 말투: "지원 활동 분석은 StatusHistory 데이터를 기반으로 향후 추가할 계획입니다."

P2. 운영 안정성
--------------------------------------------------------------------------------

[분류: 보완 필요] 관리자 업로드 원자성·실패 행 다운로드
--------------------------------------------------------------------------------

문제: bulk API는 transaction 없이 createMany를 사용하고, 실패 행을 구분하지 않는다.

구현:
- prisma.$transaction으로 createMany 감싸기
- 행별 결과 기록
- 실패 행 CSV 다운로드 API

동작: 대량 등록 중 일부 실패 시에도 나머지가 안전하게 처리되고, 실패 행을 확인할 수 있다.

사용자 가치: 잘못된 데이터가 부분적으로만 들어가는 위험 감소.

현재 한계: transaction 미적용.

[분류: 보완 필요] GitHub 외부 요청 보안
--------------------------------------------------------------------------------

문제: GitHub API 호출에 timeout, redirect, 응답 크기, rate limit 체크가 없다.

구현:
- fetch timeout 추가
- redirect policy 제한
- 응답 크기 제한
- GitHub rate limit 60회/시간 체크
- 7일 캐싱 정책 강제

동작: 외부 요청이 서비스를 멈추게 하지 않는다.

사용자 가치: 외부 URL 분석 안정성과 개인정보 보호.

현재 한계: 보호 장치 없음.

--------------------------------------------------------------------------------

[분류: 보완 필요] 알림 모델 구조화
--------------------------------------------------------------------------------

문제: UserNotification이 title/body만 있어서, 중복 방지와 클릭 시 이동이 어렵다.

구현:
- UserNotification에 type, referenceId, actionUrl 추가
- unique constraint 추가

동작: 같은 지원 건/같은 사유의 알림이 중복 생성되지 않고, 클릭 시 해당 지원 건으로 이동.

사용자 가치: 알림을 신뢰할 수 있는 행동 유도 수단으로 만든다.

현재 한계: body 문자열 contains 기반 중복 방지.

5. 최종 추천 구현 순서
================================================================================

데모 기준 1~2주 안에 핵심 흐름을 단단하게 만들려면:

1. P0-1: 지원 건과 포트폴리오·면접 답변 연결
2. P0-2: 준비율 실제 데이터 기반 개선
3. P0-3: API 보안·권한 정리
4. P1-4: 회사·공고 조사 노트
5. P1-5: 면접 회고
6. P1-6: 기술 증거 매핑
7. P1-7: ATS 형식 체크리스트
8. P1-8: 지원 활동 분석
9. P2-9 ~ P2-11: 운영 안정성
10. P3-12: 리크루터 학생 탐색

가장 효과가 큰 3가지:
1. 지원 건과 포트폴리오·면접 답변 연결
2. 기술 증거 매핑
3. 회사·공고 조사 노트

이 세 가지가 구현되면 JobFilter는 단순 관리 도구를 넘어, "이 공고에 지원하려면 어떤 증거를 준비해야 하는가"를 알려주는 서비스가 된다.

================================================================================
6. 발표 원고 핵심 문장
================================================================================

표지/소개:
> JobFilter는 공고를 보여주는 데서 끝나지 않고, 지원 건 하나에 공고·자소서·경험·면접·포트폴리오·일정·노트를 모두 연결하는 학과 맞춤형 취업 준비 플랫폼입니다.

문제 정의:
> 학교 공고 Excel은 직무가 섞여 있고, 공고를 찾은 뒤의 준비 과정이 여러 화면과 메모로 흩어져 있습니다.

차별점:
> 외부 서비스(Jobotrak, ApplyArc, Jobscan, Prentus)도 맥락 연결과 증거 매핑에 집중합니다. JobFilter는 AI API 비용 없이 rule 기반으로 이 흐름을 구현하고 있으며, 현재 핵심 데이터 연결의 1차 기반을 완료했습니다.

현재 상태:
> 공고 탐색·매칭·지원 관리·자소서 분석·경험 저장소·포트폴리오·면접·캘린더·관리자 업로드는 구현되어 있습니다. 다만 포트폴리오와 면접 답변이 지원 건에 직접 연결되지 않고, 일부 API 보안과 운영 안정성은 보완이 필요합니다.

향후 방향:
> 지원 건별 포트폴리오·면접 연결, 기술 증거 매핑, 회사 조사 노트, 면접 회고, ATS 형식 체크, 지원 활동 분석을 추가하면 단순 리스트에서 취업 준비 증거 중심 플랫폼으로 발전할 수 있습니다.

주의 문장:
> 매칭 점수는 합격 가능성이 아니라 참고 지표입니다. 자소서 분석은 AI 합격 판정이 아니라 작성 보조 피드백입니다. Today’s Tasks는 현재 개발 범위에서 제외되었습니다. 별도 /today 페이지는 없습니다.
