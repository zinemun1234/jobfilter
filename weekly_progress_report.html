JobFilter · 금주 진도 보고개선 방향

AI 기능을 현재 적용하지 않은 이유

AI를 적용하지 않은 것은 기술적 제약 때문이 아니라, 현재 서비스의 목적과 운영 조건을 고려한 선택입니다. JobFilter는 우선 설명 가능한 rule-based 분석과 사용자가 직접 입력한 경험 데이터를 중심으로 운영하는 방향을 유지합니다.

판단 근거

운영 비용

학생 대상 서비스에서 자소서·면접·매칭에 LLM API를 연결하면 사용량에 따른 비용이 발생합니다. 현재 룰 기반 방식은 별도 API 비용 없이 운영할 수 있습니다.

정확성과 오해

AI 피드백이 합격·불합격 예측처럼 받아들여질 가능성이 있습니다. 현재는 분석 결과를 합격 판정이 아닌 작성 보조 피드백으로 제한하는 것이 적절합니다.

개인정보와 동의

자소서, 면접 답변, 포트폴리오, 경험 데이터는 민감할 수 있습니다. 외부 API 전송 전 동의, 보관, 삭제, 감사 정책이 필요합니다.

개발 우선순위

현재는 AI 기능보다 지원 건과 자료를 연결하고 API 권한과 DTO를 정리하는 작업이 사용자 가치와 운영 안정성에 더 직접적입니다.

현재 방식의 한계와 보완 방향

룰 기반 분석은 문맥을 완전히 이해하지 못합니다. 예를 들어 특정 표현을 문제 문장으로 표시하더라도 실제 문맥에 따라 적절한 표현일 수 있습니다. 따라서 분석 결과는 사용자가 수정 여부를 판단하는 참고 자료로 안내해야 합니다. 향후 AI를 검토하더라도 룰 기반 결과를 대체하기보다는, 비용과 개인정보 정책이 정리된 범위에서 보조 기능으로 점진적으로 도입하는 방식이 적절합니다.

발표 시 설명: “AI를 사용하지 않는 것은 기능을 포기한 것이 아니라 현재 서비스의 비용, 개인정보, 정확성 문제를 고려해 설명 가능한 분석을 우선한 것입니다. 데이터와 운영 정책이 충분히 준비되면 제한적인 보조 기능으로 검토할 수 있습니다.”

데이터 연결 기준이 서로 다름

자소서의 jobId는 지원 건인 JobPosting을 연결하지만, JD 키워드 히트맵은 공고 데이터인 JobListing을 기준으로 비교합니다. 현재는 사용자가 공고를 직접 선택하는 방식으로 동작하며, 이후 지원 건과 공고 모델의 연결 기준을 통일해야 합니다.

운영 DB 반영 여부 확인 필요

Experience 모델과 migration 파일은 준비되어 있지만, 로컬 DB 동기화와 운영 DB migration 적용은 별개의 작업입니다. 운영 환경에서는 DATABASE_URL과 DIRECT_URL을 확인한 뒤 배포 절차를 진행해야 합니다.

외부 요청 안정성

GitHub 분석처럼 외부 API를 호출하는 기능은 응답 지연, rate limit, 잘못된 URL에 대한 보호가 필요합니다. 현재 기능은 기본 흐름을 확인한 상태이고 운영 전 보호 로직을 추가해야 합니다.

리크루터 정책 범위

리크루터 공고 등록·승인 기능과 학생 프로필 공개는 별개의 문제입니다. 학생 공개 동의, 정보 마스킹, 관심 요청, 연락처 공개 시점을 먼저 정책으로 정리해야 합니다.

알림의 구조화 부족

현재 알림은 제목과 본문 중심으로 동작하기 때문에 어떤 지원 건과 관련된 알림인지, 클릭했을 때 어느 화면으로 이동할지 명확하지 않습니다. 모델 필드 확장이 필요합니다.

종합 코멘트: 이번 주 분석을 통해 JobFilter의 핵심 문제는 기능 부족이 아니라 기능 간 연결과 운영 기준의 일관성이라는 점을 확인했습니다. 차주부터는 기능 수를 늘리는 것보다 지원 건을 중심으로 데이터와 API를 정리하는 방향이 적절합니다.
