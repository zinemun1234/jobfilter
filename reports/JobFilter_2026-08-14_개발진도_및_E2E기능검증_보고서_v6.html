01.next/trace EPERM build 실패

왜 그렇게 나왔는가

npx next build를 실행하면 Next.js는 빌드 과정의 성능·에러 추적 로그를 .next/trace 파일에 기록한다. Windows 개발 환경에서 이전 npm run dev 세션이나 예기치 않게 종료된 Node 프로세스가 해당 파일 핸들을 계속 점유하고 있으면, 빌드 스크립트가 파일을 덮어쓰거나 열려고 할 때 EPERM: operation not permitted, open '.next\trace' 오류가 발생한다. Windows Defender 등 실시간 검색 엔진이 .next 폴더를 스캔 중이면 핸들 해제가 지연되어 동일한 현상이 나타날 수도 있다.

왜 그렇게 했는가

.next 폴더는 Next.js가 생성하는 캐시/빌드 아티팩트 집합이다. 이 폴더가 잠긴 상태에서 빌드를 반복하면 단순히 재시도해도 같은 파일에 계속 접근하지 못하므로 근본적으로 핸들을 해제하고 캐시를 제거해야 한다. 또한 trace 파일은 빌드 내부용 파일이므로 사용자가 손으로 수정할 수 없고, 프로세스 단위로 정리하는 것이 가장 안전하다.

어떻게 해결했는가

먼저 남아 있는 Node 프로세스를 확인하고 종료했다. PowerShell에서는 Get-Process node | Stop-Process -Force, cmd에서는 taskkill /f /im node.exe로 강제 종료했다. 이후 .next 폴더 전체를 삭제하고 npx next build를 재실행하여 깨끗한 상태에서 빌드가 시작되도록 했다. 추가로 개발 서버를 종료한 뒤에만 production build를 수행하고, 필요한 경우 Windows Defender 예외 항목에 프로젝트 루트를 등록하는 운영 가이드를 정리했다.

02PowerShell curl 호환성 이슈

왜 그렇게 나왔는가

Windows PowerShell에는 curl이 Invoke-WebRequest의 별칭으로 등록되어 있다. 팀원이나 테스트 스크립트에서 흔히 쓰는 curl -X POST -H 'Content-Type: application/json' -d '{...}' 형식을 PowerShell 프롬프트에 그대로 입력하면, -X, -H, -d 스위치를 Invoke-WebRequest가 예상대로 해석하지 못해 헤더가 누락되거나 본문이 잘못 전송된다. 특히 작은따옴표와 중괄호는 PowerShell의 문자열/해석 규칙과 충돌하여 예상과 전혀 다른 요청이 나가거나 오류가 발생한다.

왜 그렇게 했는가

API를 수동으로 점검할 때 항상 Git Bash나 별도 터미널만 쓸 수는 없다. Windows 기본 환경에서도 신뢰할 수 있는 smoke test 방법이 필요했고, PowerShell 사용자가 실수하지 않도록 명확한 대안을 제시하는 것이 운영 안정성을 높이는 데 더 효과적이라 판단했다.

어떻게 해결했는가

두 가지 방법을 정리했다. 첫째, 실제 cURL 바이너리를 호출하려면 curl.exe라고 풀네임을 쓰고 이중 따옴표로 헤더와 JSON 본문을 감싼다. 둘째, PowerShell 네이티브 명령인 Invoke-RestMethod -Method POST -Headers @{'Content-Type'='application/json'} -Body (ConvertTo-Json @{...}) -Uri ... 형식을 사용한다. 테스트 가이드 문서에 두 방식을 예제와 함께 추가하여 앞으로의 API smoke test에서 호환성 문제를 방지했다.

03React Query 캐시 stale 문제

왜 그렇게 나왔는가

/jobs/[id] 페이지는 ['job', id] 쿼리 키로 공고 상세 정보를 가져온다. 사용자가 먼저 상세 페이지를 열어두면 이 쿼리가 캐시에 저장된다. 이후 /portfolio, /cover-letter, /interview에서 새로운 자료를 저장해도 저장 성공 콜백에서 ['job', id] 쿼리를 무효화하지 않았기 때문에, 사용자가 다시 /jobs/[id]로 돌아갔을 때 이전에 캐시된 빈 데이터가 그대로 표시되었다. 이는 React Query가 기본적으로 stale 데이터를 재사용하기 때문에 발생하는 전형적인 무효화 누락 현상이다.

왜 그렇게 했는가

사용자가 저장 직후 상세 페이지로 돌아왔을 때 최신 연결 자료를 보여줘야 "연결된 준비 자료" 기능의 신뢰성이 확보된다. 개별 저장 폼에서는 ['portfolios']나 ['experiences'] 같은 자신의 목록 쿼리만 무효화하고 있었는데, /jobs/[id] 페이지의 ['job', id] 쿼리도 함께 무효화해야 상세 페이지가 최신 데이터를 다시 불러온다. 가장 범용적이면서 안전한 방법은 queryClient.invalidateQueries를 ['job'] 키로 추가하는 것이다.

어떻게 해결했는가

포트폴리오, 경험, 면접 답변 저장/수정 후 실행되는 onSuccess 콜백에 queryClient.invalidateQueries({ queryKey: ['job'] })를 추가했다. 적용 파일은 app/(dashboard)/portfolio/page.tsx, components/cover-letter/ExperienceLibrary.tsx, components/interview/AnswerSlideOver.tsx이다. 이후 E2E에서 공고 상세 페이지를 재방문하면 최신 연결 자료가 바로 표시되는 것을 확인했다.

04/api/jobs userId 노출

왜 그렇게 나왔는가

app/api/jobs/[id]/route.ts에서는 sanitizeJobPosting()을 적용해 userId와 user 관계를 제거했지만, app/api/jobs/route.ts의 목록 조회(GET)와 새 공고 생성(POST) 응답에서는 Prisma에서 반환하는 객체를 그대로 JSON으로 내려주고 있었다. JobPosting 레코드는 userId 외래키를 포함하고 있으므로 클라이언트에게 사용자 식별자가 그대로 노출되었다.

왜 그렇게 했는가

프론트엔드에서 공고 목록이나 생성 결과를 받을 때 userId는 전혀 필요하지 않다. 오히려 다른 사용자의 userId가 공개될 경우 보안 리스크가 되므로, API 응답 DTO 변환을 체계적으로 적용해야 한다. lib/api.ts에 이미 sanitizeJobPosting()이 준비되어 있었으므로 재사용하는 것이 일관성과 유지보수성 측면에서 옳다.

어떻게 해결했는가

app/api/jobs/route.ts에서 GET/POST 응답 직전에 sanitizeJobPosting()을 호출하도록 수정했다. 목록의 각 항목과 새로 생성된 단일 항목 모두 sanitize를 거쳐 userId와 user 객체가 제거된 상태로 클라이언트에 전달된다. 이후 브라우저 개발자 도구 Network 탭으로 확인한 결과 /api/jobs 응답에 민감 필드가 포함되지 않았다.

05useSearchParams static-rendering 이슈

왜 그렇게 나왔는가

app/open/listings/page.tsx는 client 컴포넌트로 작성되어 있고, 필터 값을 읽기 위해 useSearchParams() 훅을 직접 사용했다. Next.js 14는 static generation 단계에서 client hook을 만나면 자동으로 CSR bail-out을 시도하지만, 이 페이지에 적절한 <Suspense> 경계가 없어 next build에서 prerender 실패 오류를 내보낸다. 기존에 추가되어 있던 export const dynamic = 'force-dynamic'는 server 컴포넌트에 의미가 있지 client 페이지에는 영향을 주지 않아 실효성이 없었다.

왜 그렇게 했는가

검색/필터 기능은 query string에 의존하므로 client hook 사용 자체는 정당하다. 다만 Next.js App Router는 client hook을 포함한 페이지를 Suspense boundary로 감싸야 build 시점에 안정적으로 처리할 수 있다. 따라서 페이지 전체를 Suspense로 감싸고, client 페이지에서 의미 없는 dynamic = 'force-dynamic'은 제거하여 의도를 명확히 하는 것이 맞다.

어떻게 해결했는가

app/open/listings/page.tsx의 본문을 <Suspense fallback={<div>로딩 중...</div>}> 내부로 이동시켰다. 기존 export const dynamic = 'force-dynamic' 선언은 제거했다. 동일한 패턴이 useSearchParams를 사용하는 다른 client 페이지에도 적용될 수 있도록 점검하여 build가 깨끗이 통과하도록 했다.

01 AI API 연동 검토

본 항목은 차주(P0/P1)가 아닌 장기적으로 검토해야 할 계획이다. JobFilter는 rule-based/keyword 기반으로 핵심 기능을 먼저 안정화한 뒤, AI API를 옵션으로 확장하는 방향으로 검토한다.

  • JobFilter는 "이 공고에 지원하려면 무슨 근거를 준비해야 하는가"를 답하는 것이 목표
  • 자소서 분석, 공고 추천, 면접 코칭에 AI를 쓰면 사용자 경험을 높일 수 있다
  • 하지만 AI API는 비용, 정확도, 개인정보 처리, 외부 의존성 등 검토가 필요한 장기 사항
  • rule-based/keyword 기반으로 먼저 안정화하고, 이후 옵션으로 추가하는 것이 리스크가 적음

E2E 기능 검증

검증 목적

Next.js production build 기반 브라우저 자동화로 사용자/관리자 핵심 페이지와 주요 인터랙션이 정상적으로 렌더링되고 동작하는지 종합적으로 확인한다.

Next.js 14.2.5 production build를 http://localhost:3000에서 실행하고, admin@admin.com 관리자 계정으로 로그인한 상태에서 브라우저 자동화 도구를 활용해 실제 사용자 흐름을 재현하고 스크린샷과 인터랙션을 캡처한다.
