01.next/trace EPERM build 실패

왜 그렇게 나왔는가

npx next build를 실행하면 Next.js는 빌드 과정의 성능·에러 추적 로그를 .next/trace 파일에 기록한다. Windows 개발 환경에서 이전 npm run dev 세션이나 예기치 않게 종료된 Node 프로세스가 해당 파일 핸들을 계속 점유하고 있으면, 빌드 스크립트가 파일을 덮어쓰거나 열려고 할 때 EPERM: operation not permitted, open '.next\trace' 오류가 발생한다. Windows Defender 등 실시간 검색 엔진이 .next 폴더를 스캔 중이면 핸들 해제가 지연되어 동일한 현상이 나타날 수도 있다.

왜 그렇게 했는가

.next 폴더는 Next.js가 생성하는 캐시/빌드 아티팩트 집합이다. 이 폴더가 잠긴 상태에서 빌드를 반복하면 단순히 재시도해도 같은 파일에 계속 접근하지 못하므로 근본적으로 핸들을 해제하고 캐시를 제거해야 한다. 또한 trace 파일은 빌드 내부용 파일이므로 사용자가 손으로 수정할 수 없고, 프로세스 단위로 정리하는 것이 가장 안전하다.

어떻게 해결했는가

먼저 남아 있는 Node 프로세스를 확인하고 종료했다. PowerShell에서는 Get-Process node | Stop-Process -Force, cmd에서는 taskkill /f /im node.exe로 강제 종료했다. 이후 .next 폴더 전체를 삭제하고 npx next build를 재실행하여 깨끗한 상태에서 빌드가 시작되도록 했다. 추가로 개발 서버를 종료한 뒤에만 production build를 수행하고, 필요한 경우 Windows Defender 예외 항목에 프로젝트 루트를 등록하는 운영 가이드를 정리했다.

02PowerShell curl 호환성 이슈

왜 그렇게 나왔는가

Windows PowerShell에는 curl이 Invoke-WebRequest의 별칭으로 등록되어 있다. 팀원이나 테스트 스크립트에서 흔히 쓰는 curl -X POST -H 'Content-Type: application/json' -d '{...}' 형식을 PowerShell 프롬프트에 그대로 입력하면, -X, -H, -d 스위치를 Invoke-WebRequest가 예상대로 해석하지 못해 헤더가 누락되거나 본문이 잘못 전송된다. 특히 작은따옴표와 중괄호는 PowerShell의 문자열/해석 규칙과 충돌하여 예상과 전혀 다른 요청이 나가거나 오류가 발생한다.

왜 그렇게 했는가

API를 수동으로 점검할 때 항상 Git Bash나 별도 터미널만 쓸 수는 없다. Windows 기본 환경에서도 신뢰할 수 있는 smoke test 방법이 필요했고, PowerShell 사용자가 실수하지 않도록 명확한 대안을 제시하는 것이 운영 안정성을 높이는 데 더 효과적이라 판단했다.

어떻게 해결했는가

두 가지 방법을 정리했다. 첫째, 실제 cURL 바이너리를 호출하려면 curl.exe라고 풀네임을 쓰고 이중 따옴표로 헤더와 JSON 본문을 감싼다. 둘째, PowerShell 네이티브 명령인 Invoke-RestMethod -Method POST -Headers @{'Content-Type'='application/json'} -Body (ConvertTo-Json @{...}) -Uri ... 형식을 사용한다. 테스트 가이드 문서에 두 방식을 예제와 함께 추가하여 앞으로의 API smoke test에서 호환성 문제를 방지했다.

03React Query 캐시 stale 문제

왜 그렇게 나왔는가

/jobs/[id] 페이지는 ['job', id] 쿼리 키로 공고 상세 정보를 가져온다. 사용자가 먼저 상세 페이지를 열어두면 이 쿼리가 캐시에 저장된다. 이후 /portfolio, /cover-letter, /interview에서 새로운 자료를 저장해도 저장 성공 콜백에서 ['job', id] 쿼리를 무효화하지 않았기 때문에, 사용자가 다시 /jobs/[id]로 돌아갔을 때 이전에 캐시된 빈 데이터가 그대로 표시되었다. 이는 React Query가 기본적으로 stale 데이터를 재사용하기 때문에 발생하는 전형적인 무효화 누락 현상이다.

왜 그렇게 했는가

사용자가 저장 직후 상세 페이지로 돌아왔을 때 최신 연결 자료를 보여줘야 "연결된 준비 자료" 기능의 신뢰성이 확보된다. 개별 저장 폼에서는 ['portfolios']나 ['experiences'] 같은 자신의 목록 쿼리만 무효화하고 있었는데, /jobs/[id] 페이지의 ['job', id] 쿼리도 함께 무효화해야 상세 페이지가 최신 데이터를 다시 불러온다. 가장 범용적이면서 안전한 방법은 queryClient.invalidateQueries를 ['job'] 키로 추가하는 것이다.

어떻게 해결했는가

포트폴리오, 경험, 면접 답변 저장/수정 후 실행되는 onSuccess 콜백에 queryClient.invalidateQueries({ queryKey: ['job'] })를 추가했다. 적용 파일은 app/(dashboard)/portfolio/page.tsx, components/cover-letter/ExperienceLibrary.tsx, components/interview/AnswerSlideOver.tsx이다. 이후 E2E에서 공고 상세 페이지를 재방문하면 최신 연결 자료가 바로 표시되는 것을 확인했다.

04/api/jobs userId 노출

왜 그렇게 나왔는가

app/api/jobs/[id]/route.ts에서는 sanitizeJobPosting()을 적용해 userId와 user 관계를 제거했지만, app/api/jobs/route.ts의 목록 조회(GET)와 새 공고 생성(POST) 응답에서는 Prisma에서 반환하는 객체를 그대로 JSON으로 내려주고 있었다. JobPosting 레코드는 userId 외래키를 포함하고 있으므로 클라이언트에게 사용자 식별자가 그대로 노출되었다.

왜 그렇게 했는가

프론트엔드에서 공고 목록이나 생성 결과를 받을 때 userId는 전혀 필요하지 않다. 오히려 다른 사용자의 userId가 공개될 경우 보안 리스크가 되므로, API 응답 DTO 변환을 체계적으로 적용해야 한다. lib/api.ts에 이미 sanitizeJobPosting()이 준비되어 있었으므로 재사용하는 것이 일관성과 유지보수성 측면에서 옳다.

어떻게 해결했는가

app/api/jobs/route.ts에서 GET/POST 응답 직전에 sanitizeJobPosting()을 호출하도록 수정했다. 목록의 각 항목과 새로 생성된 단일 항목 모두 sanitize를 거쳐 userId와 user 객체가 제거된 상태로 클라이언트에 전달된다. 이후 브라우저 개발자 도구 Network 탭으로 확인한 결과 /api/jobs 응답에 민감 필드가 포함되지 않았다.

05useSearchParams static-rendering 이슈

왜 그렇게 나왔는가

app/open/listings/page.tsx는 client 컴포넌트로 작성되어 있고, 필터 값을 읽기 위해 useSearchParams() 훅을 직접 사용했다. Next.js 14는 static generation 단계에서 client hook을 만나면 자동으로 CSR bail-out을 시도하지만, 이 페이지에 적절한 <Suspense> 경계가 없어 next build에서 prerender 실패 오류를 내보낸다. 기존에 추가되어 있던 export const dynamic = 'force-dynamic'는 server 컴포넌트에 의미가 있지 client 페이지에는 영향을 주지 않아 실효성이 없었다.

왜 그렇게 했는가

검색/필터 기능은 query string에 의존하므로 client hook 사용 자체는 정당하다. 다만 Next.js App Router는 client hook을 포함한 페이지를 Suspense boundary로 감싸야 build 시점에 안정적으로 처리할 수 있다. 따라서 페이지 전체를 Suspense로 감싸고, client 페이지에서 의미 없는 dynamic = 'force-dynamic'은 제거하여 의도를 명확히 하는 것이 맞다.

어떻게 해결했는가

app/open/listings/page.tsx의 본문을 <Suspense fallback={<div>로딩 중...</div>}> 내부로 이동시켰다. 기존 export const dynamic = 'force-dynamic' 선언은 제거했다. 동일한 패턴이 useSearchParams를 사용하는 다른 client 페이지에도 적용될 수 있도록 점검하여 build가 깨끗이 통과하도록 했다.

SMTP / DTO 세부 검토

10
06-1 SMTP (비밀번호 재설정 메일 발송)

왜 필요한가

비밀번호 재설정은 계정 복구의 핵심 경로로, 사용자 신뢰과 보안 모두에 직접 영향을 준다. 현재는 안내 메시지만 표시되고 실제 메일은 발송되지 않아 production 배포 전 반드시 메일 발송 연동이 필요하다.

어떻게 구현하는가

  • 발송 채널: Resend를 권장한다. Next.js App Router와 자연스럽게 맞고, API 기반이며 SMTP 인프라를 직접 관리할 필요가 없다. 기존 메일 서버가 있다면 Nodemailer/SMTP도 사용할 수 있다.
  • 토큰 설계: crypto.randomBytes(32).toString('hex') 또는 crypto.randomUUID()로 생성하고, 만료는 15~30분으로 제한한다. DB에 PasswordResetToken 모델(token, email, type, expiresAt, used)을 두어 1회용 사용 후 삭제하거나 used를 표시한다.
  • 메일 발송: resend.emails.send({ from: "JobFilter <noreply@도메인>", to: email, subject: "비밀번호 재설정", html: ... }) 형태로 발송한다. reset URL은 ${NEXTAUTH_URL}/reset-password?token=...로 구성한다.
  • 보안: HTTPS URL, token 만료, 1회용 처리, 메일 발송 실패 시에도 동일한 안내 메시지를 노출해 계정 존재 여부를 유추하지 못하게 한다.

변경 파일

  • app/api/auth/forgot-password/route.ts — 메일 발송
  • app/reset-password/page.tsx 또는 app/(auth)/reset-password/page.tsx — 새 비밀번호 입력
  • prisma/schema.prisma — PasswordResetToken 모델 추가
  • lib/tokens.ts 또는 lib/email.ts — 토큰/메일 헬퍼
06-2 DTO sanitize

왜 필요한가

API 응답에서 password, userId, user 등 민감하거나 불필요한 내부 식별자가 노출되지 않아야 한다. 이는 개인정보 보호 기준을 충족하는 기본 조치이며, 프론트엔드에서 실제로 필요 없는 필드를 제거해 응답 크기와 복잡도도 줄인다.

어떻게 구현하는가

  • Prisma 5.16+ omit: 글로벌 클라이언트에서는 new PrismaClient({ omit: { user: { password: true } } }), 쿼리별로는 prisma.user.findMany({ omit: { password: true } })를 사용한다.
  • select 옵션으로 DB 조회 시 필요한 필드만 명시해 처음부터 민감정보를 가져오지 않는다.
  • DTO mapper/serializer: lib/api.ts의 sanitizeUser(), sanitizeJobPosting() 등으로 응답 직전 일관되게 필터링한다.
  • 권장: omit 글로벌 설정과 select 조합, 또는 sanitize 함수를 일관되게 적용한다.

변경 파일

  • /api/portfolio/*
  • /api/experiences/*
  • /api/interview/answers/*
  • /api/admin/users/*
  • 검증: 브라우저 Network 탭 및 테스트 코드에서 userId/password 미포함 확인

4. 이 조사가 JobFilter에 주는 시사점

본 조사는 JobFilter가 Next.js + Prisma + PostgreSQL 기반으로 동일한 문제를 해결할 때, 오픈소스 사례에서 검증된 SMTP 및 DTO sanitize 패턴을 어떻게 적용할지에 대한 근거를 제시한다. 따라서 이 페이지는 단순한 참고 자료가 아니라 차주 실무 계획의 직접적인 기반이 된다.

1. 왜 이 조사를 했는가

  • JobFilter도 Next.js + Prisma + PostgreSQL 기반이다.
  • 비밀번호 재설정과 API 응답 보안은 JobFilter의 현재 미완료 항목이다.
  • 실제 오픈소스 프로젝트들이 어떻게 해결했는지 확인하고, JobFilter에 맞는 적용 방향을 도출하기 위함이다.

2. SMTP 적용 방향

  • forgot-password에서 개발용 devToken 응답을 제거하고 Resend 연동으로 전환한다.
  • PasswordResetToken Prisma 모델을 추가한다. (token, email, type, expiresAt, used)
  • reset token은 crypto.randomBytes(32) 또는 crypto.randomUUID()로 생성한다.
  • 만료 시간은 15~30분, 1회용 사용 후 삭제/used 처리한다.
  • reset URL은 ${NEXTAUTH_URL}/reset-password?token=... 형태로 발송한다.
  • 관련 파일: app/api/auth/forgot-password/route.ts, app/reset-password/page.tsx, prisma/schema.prisma

3. DTO sanitize 적용 방향

  • /api/jobs에 이미 적용된 sanitizeJobPosting() 패턴을 확대한다.
  • /api/portfolio/*, /api/experiences/*, /api/interview/answers/*, /api/admin/users/* 응답에서도 userId, password, user 객체를 제거한다.
  • 방법:
    • 방법 A: PrismaClient 전역 omit: { user: { password: true } } 설정 (Prisma 5.16+)
    • 방법 B: 쿼리별 select/omit 사용
    • 방법 C: lib/api.ts의 sanitizeUser(), sanitizeJobPosting() 헬퍼 일관 적용
  • 브라우저 Network 탭과 테스트 코드로 민감 필드 노출 여부 검증

4. 왜 필요한가

  • production 배포 시 사용자 password, userId 등이 응답에 노출되면 보안 사고로 이어진다.
  • 비밀번호 재설정은 실제 서비스 운영의 최소 조건이다.
  • OWASP A01(Broken Access Control), CWE-200(민감정보 노출) 대응
  • 사용자 신뢰 및 개인정보 보호 규격 준수

5. 차주 계획과의 연결

  • 차주 계획의 P0 항목인 SMTP 연동과 API 응답 DTO sanitize 확대가 이 조사 결과를 바탕으로 진행된다.
  • 즉, 이 페이지는 단순 참고 자료가 아니라 차주 실무 계획의 근거가 된다.

08 차주(단기) 실행 계획

production 배포 직전에 반드시 마무리해야 할 항목부터 순차적으로 정리했다. 우선순위는 실제 서비스 운영 가능 여부, 보안 리스크, 사용자 경험 영향, 의사결정 시급성을 기준으로 선정했다. 차주 실행은 장기 개선 로드맵의 기초가 되며, 서비스가 운영 환경에서 안정적으로 돌아간 뒤에야 고도화/AI 확장 검토가 가능하다.

우선순위 선정 근거 항목 내용
P0 사용자 가입/로그인/비밀번호 재설정은 서비스 운영의 전제조건이며, 현재 메일 발송이 완전히 안 되어 배포 블로커. SMTP 연동 비밀번호 재설정 메일을 실제로 발송할 수 있도록 Resend 또는 Nodemailer를 연동한다. 현재는 안내 메시지만 노출되고 메일은 발송되지 않는다.
P0 userId, password 등 민감정보가 API 응답에 노출되면 OWASP A01/CWE-200에 해당하는 보안 사고로 이어짐. API 응답 DTO sanitize 확대 /api/jobs는 정리되었지만, /api/portfolio/*, /api/experiences/*, /api/interview/answers/*, /api/admin/users/* 등에서 아직 userId, password 등 민감정보가 노출될 수 있다. sanitizeUser(), sanitizeJobPosting() 등을 일관되게 적용한다.
P0 npx next build는 통과했지만 실제 운영 환경 배포와 환경변수 검증이 없으면 production 사용 불가. Vercel 배포 DATABASE_URL, NEXTAUTH_SECRET, NEXTAUTH_URL, SMTP 관련 환경변수를 Vercel 프로젝트에 등록하고 production 배포를 수행한다.
P1 배포 후 운영 안정성과 유지보수성을 위해 기존 데이터 구조 정리 및 불필요한 코드 제거가 필요. 데드라인은 P0보다 유연. 데이터 정리 기존 UserNotification 데이터의 referenceId를 알림 종류에 맞게 백필하고, 사용하지 않는 devToken 관련 코드·주석·console.log를 제거한다.
P1 배포 후 사용자 경험과 관리자 운영 효율에 직접 영향. 핵심 기능은 완료되었으나 다듬어야 할 세부 UX. UX/기능 다듬기 /jobs/[id]의 연결 자료 카드를 클릭하면 실제 포트폴리오/경험/면접 페이지로 이동하도록 연결하고, 연결 해제 기능, 드롭다운 로딩/빈 상태 처리 및 검색/필터를 추가한다. 관리자 페이지에서도 각 자료가 어떤 공고에 연결되었는지 표시한다.
장기 개선 로드맵

차주(단기) 실행이 마무리된 이후에 검토할 장기 항목을 별도로 정리했다. 비용, 정확도, 개인정보, 외부 의존성 등 검토가 필요한 선택 사항이며, rule-based 코어가 안정된 후 단계적으로 도입한다.

01 AI API 연동 검토

본 항목은 차주(P0/P1)가 아닌 장기적으로 검토해야 할 계획이다. JobFilter는 rule-based/keyword 기반으로 핵심 기능을 먼저 안정화한 뒤, AI API를 옵션으로 확장하는 방향으로 검토한다.

  • JobFilter는 "이 공고에 지원하려면 무슨 근거를 준비해야 하는가"를 답하는 것이 목표
  • 자소서 분석, 공고 추천, 면접 코칭에 AI를 쓰면 사용자 경험을 높일 수 있다
  • 하지만 AI API는 비용, 정확도, 개인정보 처리, 외부 의존성 등 검토가 필요한 장기 사항
  • rule-based/keyword 기반으로 먼저 안정화하고, 이후 옵션으로 추가하는 것이 리스크가 적음
02 적용 가능 영역
  • 자소서 분석: 키워드/패턴 강점·약점 피드백
  • 공고 추천: 사용자 기술 스택/경험과 공고 내용 매칭
  • 면접 코칭: 질문 의도 분석, 모범 답변 구조 제안

05 구현 방향
  • 초기: rule-based + keyword-only로 자소서 분석/공고 매칭 안정화 (현재 상태)
  • 1단계: server-side API route에서 Gemini API 호출, 결과를 rule-based 가드레일로 후처리
  • 2단계: 공고 추천, 면접 코칭에 확대
  • API key는 .env에만 보관, client로 절대 노출하지 않음
  • AI 분석 결과는 "참고용"으로 명시, 사용자 최종 판단 우선
06 관련 파일
  • app/api/cover-letter/analyze/route.ts — 자소서 분석
  • app/api/jobs/recommend/route.ts — 공고 추천
  • app/api/interview/coach/route.ts — 면접 코칭
  • lib/ai.ts — AI 호출 추상화, timeout/rate limit/fallback 처리
07 판단

AI API 연동은 사용자 경험을 높일 수 있지만, 비용·정확도·개인정보·외부 의존성 검토가 필요하다. 따라서 장기 계획으로 분류하고, rule-based 코어가 안정된 후 단계적으로 도입한다.
